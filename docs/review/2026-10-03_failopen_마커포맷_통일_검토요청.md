# 재판정 마커 포맷 통일 + gate 원본 복원 — 설계 검토 요청

- **작성일**: 2026-10-03
- **검토 대상**: jev-memory-middleware fail-open 재판정 파이프라인의 마커 포맷 단일화 및 gate 감사 이력 복원 (P1~P3a 산출물 정리)
- **검토 의뢰 사유**: 96행 데이터 마이그레이션 + 신규 기록 코드 표준 변경을 수반하는 역호환 민감 작업. 구현 전에 외부 의견으로 설계를 확정하고자 함.

## 1. 배경 (한 문단 요약)

JEV API(외부 유료 LLM 판정 API) 장애(HTTP 402/403) 시 메모리 플러그인은 fail-open 정책으로 저장을 계속하되 `gate:fail_open:*` 마커를 남긴다. 이후 재판정 파이프라인(P1 수동 적용 → P2a/b 상태기계 → P3a 자동 재판정)으로 KEEP/SKIP을 판정한다. 그 과정에서 **기록 도구별로 마커 포맷이 2종으로 갈렸고**, 1차 적용 도구(P1 apply)가 `gate` 필드에 보관하던 **원본 장애 원인 값(`fail_open:http-402/403`)을 `rejudged:*`로 덮어써 감사 이력이 훼손**되었다. 운영 recall에는 현재 영향이 없으나(제외는 `valid_until` **컬럼**으로 동작), 감사·디버깅·카운트 정확도에 구조적 결함이 남아 있어 단일 포맷 + 원본 복원을 계획한다.

## 3. 제안 설계

### 3-1. Canonical 포맷 (신규 기록부 표준)

```json
{
  "gate": "fail_open:http-402",   // 장애 원인 — 불변 유지, 재판정이 절대 덮지 않음
  "rejudged": "keep" | "skip",    // 재판정 결과 — 단일 필드 (태그형 폐지)
  "rejudged_at": "2026-10-03T16:33:21",
  "archived": true,               // skip 전용
  "archived_at": "..."            // 기존 값 유지 (있을 경우)
}
```

근거: `gate`는 장애 발생 시점의 원인(불변), `rejudged`는 재판정 시점의 결과(후발) — 서로 다른 수명주기. 하나의 필드에 합성하면 원인 정보가 소실됨(실측으로 입증).

### 3-2. 데이터 백필 (96행, 1회)

1. **online backup 스냅샷** 생성 + 행 수 일치 복원 검증 (기존 `jed_failopen_403_apply.py` 스냅샷 절차 재사용)
2. **태그형 68행**: `gate` 원본 복원(스냅샷) + `rejudged` 필드 생성(keep/skip 매핑) + `rejudged_at` 복원(아래 Q3 순서) + skip 2건 `archived` 보충
3. **필드형 28행**: `gate` 유지, `rejudged_at` 누락분(4행) 보충
4. **검증**: 96행 shape 전수 확인 / skip 24행 `valid_until` 유지(recall inactive 불변) / keep 72행 active 불변 / `skip_staged` 카운트 동일

### 3-3. 코드 통일 (신규 기록부)

- `jev_mem_core/recover.py` `_apply_verdict` (P3a 자동 경로): 현재 `meta["rejudged"]=verdict`만 씀 → canonical으로
- `tools/jed_failopen_rejudge_v2.py` `_apply_verdict`: 현재 `meta["gate"]=f"rejudged:{verdict}@{model}"` (태그형!) → canonical으로
- `tools/jed_failopen_403_apply.py` 등의 과거 복원/적용 스크립트: **데이터 마이그레이션 용도로만 보존**(수정하지 않음 — 재실행 불필요)

### 3-4. 소비처 정리 (역호환 유지)

| 위치 | 현재 | 계획 |
|---|---|---|
| `jev_mem_core/server.py` skip_staged | 3중 LIKE: `%rejudged:skip%` OR `%"rejudged": "skip"%` OR 압축형 | canonical 단일 predicate (+ 기존 2형 호환 유지) |
| `jev_mem_core/recover.py` quarantine 제외 | `NOT LIKE '%rejudged%'` | 유지 (canonical도 매칭되어 무해) |
| `tools/jed_failopen_archived_recall_regress.py` 등 검증 도구 | 태그/필드 LIKE 혼용 | canonical 우선 쿼리로 갱신 |

canonical 포맷은 기존 2형 predicate 전부와 문자열 매칭되므로, 소비처 교체는 순수 정리 작업(동작 변화 없음).

### 3-5. 검증 & 롤백

- 회귀 테스트 전부 재실행: `tools/jed_failopen_archived_recall_regress.py`, `jed_failopen_p3a_verify.py`(20), `jed_failopen_p3a_syncpath_verify.py`(7)
- 라이브 데몬(`/v1/status`): `skip_staged=24`, `pending=0` 유지, recall 활성 행 수 불변
- 롤백: 백필 스냅샷으로 DB 복원 + 코드는 이전 커밋으로 revert

## 4. 검토 쟁점 (결정 필요)

**Q1. Canonical 포맷 분리(`gate` 원본 유지 + `rejudged` 별도 필드)가 타당한가?**
- 대안: (a) 현행 유지(태그형 합성), (b) 재판정 이력을 metadata 최상위가 아닌 별도 네임스페이스(예: `rejudge: {...}` 객체)에 보관
- 기준: 감사 이력 보존(402/403 구분 가능), 단순성, 기존 소비 predicate와의 문자열 호환

**Q2. 68행 `gate` 원본 복원(덮어쓰기)이 옳은가, 아니면 현행 합성 상태를 유지해야 하는가?**
- "P1 반영 시점"의 기록인 `rejudged:*`를 지우는 것이 감사 연속성을 해치지 않는지
- 원본 복원 시 재판정 이력은 `rejudged` 필드 + `rejudge_verdicts` 테이블에 남는 구조인 점을 고려

**Q3. `rejudged_at` 복원 순서(소스 우선순위)는 어떤가?**
- 제안: ① `core_state.db.rejudge_verdicts.rejudged_at`(32건 커버) → ② metadata `archived_at`(P1 태그형 skip 보유) → ③ 스냅샷 시각 fallback
- 더 정확한 소스(예: ingest_ledger.updated_at 조인, 파일 mtime)가 있는가?

**Q4. 과거 적용 스크립트(태그형 작성)를 수정 없이 보존하는 정책이 타당한가?**
- 대안: 문서에 "deprecated" 표기 추가, 또는 canonical로 수정 후 신규 실행 금지 명시
- 스크립트 보존 시 재실행 위험(중복 apply)이 있는지

**Q5. 소비 predicate 정리 범위는?**
- 제안: server.py만 canonical 우선 + 기존 2형 호환 유지. 전 도구를 canonical 전용으로 바꾸는 것 vs 현 제안 — 어느 쪽이 유지보수에 나은가?

**Q6. 계획에서 누락/과잉된 부분이 있는가?** (리스크 포함)

## 5. 의뢰자의 현재 성향

- `gate`는 "원인"(불변값), `rejudged`는 "결과"(후발값) — **분리 보관이 맞다**고 봄. 실제로 P3a 필드형 경로(24건)는 이렇게 동작했고 결함이 없었음
- 68행 원본 복원은 스냅샷 2개로 100% 커버됨을 실측 확인했으므로 **안전하다**고 봄
- 단일화 순서: 신규 기록부(코드) 우선 통일 → 과거 행은 백필 1회 → 소비처는 역호환 유지하며 정리 — 가 되겠다고 봄
- Q2(복원 vs 유지)가 가장 불확실한 지점 — 반대 의견이 있으면 특히 듣고 싶음
