## 2. 개선 설계 (3축)

### 축 1: "일반 지식 대체 가능성" 기준 재정의 (도메인 무관)

- 판정 질문을 "사용자 고유 정보를 인용했나?" → **"이 응답의 핵심 정보를 메모리 없이
  (일반 지식/추론으로)도 얻을 수 있었나?"** 로 변경
- "no" = 메모리 없이도 답할 수 있는 내용뿐 (일반 지식 대체 가능)
- "yes" = 메모리가 없으면 알 수 없는 내용 포함 (사용자 특정)
- 예시 목록(파일 경로·설정 값·실험 수치 등)을 **기준의 정의가 아니라 판정 보조 도구**로만 사용

### 축 2: no 판정만 2차 검증 (비용 최소화)

- no는 희귀 클래스 (운영 k=5 fF no 2.9%, 사용자 기준 더 낮음)
- **no 판정만** 별도 검증 경로로 — 전체의 ~4%만 추가 비용
- 2차 검증 = 축 1 재질문 + 필요 시 사람 확인

### 축 3: "구체성 신호" 규칙 스크리닝 (도메인 무관 regex)

사용자가 직접 만든 것(코드·설정·문서·실험)엔 **고유 식별자**가 따라붙는다 — 도메인 무관한 꼴:

| 신호 | regex 예 | 비고 |
|---|---|---|
| 경로 | `[A-Za-z]:\\...` · `/.../...` | OS·프로젝트 무관 |
| URL | `https?://...` | 코드·문서·웹 |
| 숫자+단위 | `\d+%` · `\d+(\.\d+)?(초\|분\|시간\|ms)` | 실험·성능·벤치 |
| 버전/해시 | `v?\d+\.\d+\.\d+` · `[0-9a-f]{7,}` | 코드·패키지·커밋 |
| 고유명사 | `[A-Z][a-z]+( [A-Z][a-z]+)+` | 제품·모델·도구 (영문) |
| 키-값 설정 | `\w+=\w+` · `key: value` | config |

- **용도**: haiku가 no라고 판정했을 때, 이 신호가 있으면 "no 의심" 플래그 (자동 재검토 트리거)
- **한계**: 텍스트형 인용(규칙 문구·원칙)은 신호가 없을 수 있음 → 축 1이 커버
- **역할**: "의심 증폭기" — 판정 대체가 아니라 1차 검증의 보조

## 3. 결합 동작

```
haiku 판정
  ├─ yes → 통과 (희귀 클래스 no만 검증하므로 yes는 신뢰)
  └─ no ─→ [축1] "일반 지식 대체 가능?" 재질문
            └─ [축3] 동시에 "구체성 신호" 스캔
                 ├─ 신호 있음 → no 의심 → 재판정 우선 (사람 or 다른 모델)
                 └─ 신호 없음 → no 유지 (일반 지식 응답)
```

- **축 1** = 텍스트 인용 커버 (축 3이 못 잡는 것)
- **축 3** = "일반 지식으로도 가능" 판정의 주관성 보완 (축 1이 놓치는 구체성 자동 탐지)
- **축 2** = 비용을 no 4%로 한정 (1·3을 전체에 돌리지 않음)
