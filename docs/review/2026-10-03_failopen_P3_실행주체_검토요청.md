# P3 자동 재판정 실행 주체 — 설계 검토 요청

- **작성일**: 2026-10-03
- **검토 대상**: jev-memory-middleware P3 (fail-open 자동 재판정) — "누가 재판정 루프를 실행하는가"
- **검토 의뢰 사유**: 핵심 설계 결정 1건 — 구현 전에 외부 의견을 받아 확정하고자 함

---

## 1. 배경 (한 문단 요약)

JEV API(외부 유료 LLM 판정 API, memory relevance 판정용) 장애 시, memory 플러그인은 fail-open 정책으로 메모리 저장을 계속하되 `quarantine` 상태로 기록한다. 장애가 끝난 후 이 quarantine된 메모리들을 JEV로 재판정해 KEEP(유지)/SKIP(삭제 후보)을 가린다. 현재 이 재판정은 CLI 도구(`tools/jed_failopen_rejudge_v2.py`)로 수동 실행한다. P3는 이 재판정을 자동화하는 단계다.

## 2. 현재까지의 설계 (이미 확정된 것)

1. **회복 감지**: 주기적 프로브 없음 (비용 발생). 실제 사용자 호출이 3회 연속 성공 + 30분 경과 시 "회복"으로 간주. 추가 호출 0.
2. **자동 재판정 루프**: 회복 감지 시 quarantine batch를 strict 모드로 재판정 (KEEP 자동 승격 / SKIP은 staged만, 최종 삭제는 수동 승인).
3. **경보/알림**: 별도 푸시 인프라 없음 (경량 원칙). 상태는 ledger/gate_outage 테이블에 기록되고 `/v1/status` 및 응답 필드로 노출. 전달은 에이전트 측(skill/plugin)이 읽는 방식.
4. **불변식**: 재판정 중 새 장애 발생 시 즉시 중단, quarantine 유지. SKIP은 항상 staged까지만.

## 3. 검토 쟁점 (결정 필요)

**"재판정 루프를 실행하는 주체"를 어디에 둘 것인가?**

| 옵션 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. core 자체 루프** | `jev_mem_core`에 백그라운드 태스크 추가 (기존 `requeue_pending_gate` 60초 루프 패턴 재사용) | 컴포넌트 +0, 모든 에이전트/게이트웨이 환경에서 실행 보장, 배포 단순 | core에 "재판정" 책임 추가 (SRP 관점) |
| **B. Hermes cron** | Hermes cron으로 재판정 도구를 주기 실행 | core 순수 유지 | Hermes 전용 — "어떤 에이전트든 동일 동작" 원칙 위배 |
| **C. 별도 가드 데몬** | 재판정 전용 프로세스 (독립 실행) | core 순수 유지, 관심사 분리 | 컴포넌트 +1, 배포/운영 복잡성 증가 |

**판단 기준 (의뢰자가 중시하는 원칙)**
- 어떤 에이전트(Hermes/Codex/Pi 등)가 쓰든 **동일하게 동작**해야 함
- 플러그인은 "메모리 서비스"로 경량 유지 — 알림 인프라/푸시 추가는 과함 (이미 기각됨)
- 구현 단순성, 유지보수 용이성
- SRP(단일 책임) 원칙 — 관심사 분리

## 4. 의뢰자의 현재 성향

- A(core 자체 루프)에 기울어 있음 — 기존 `requeue_pending_gate` 백그라운드 루프 패턴이 이미 있어 추가 비용이 낮고, "모든 환경에서 실행 보장"이 가장 중요하다고 봄
- 다만 core에 재판정 책임이 추가되는 SRP 위반 우려가 있어, A 대신 C(가드 데몬 분리)가 더 나은지 확인받고 싶음

## 5. 요청 사항

1. A/B/C 중 어느 것이 가장 적절한가? (이유 포함)
2. SRP 위반 우려(옵션 A)는 실질적인가, 아니면 이 프로젝트 규모에선 과한 걱정인가?
3. 옵션 C(가드 데몬)를 선택한다면, 데몬이 core와 통신하는 방식(상태 DB 직접 읽기 vs core API) 중 어느 쪽이 나은가?
4. 다른 대안(하이브리드 등)이 있다면 제안
