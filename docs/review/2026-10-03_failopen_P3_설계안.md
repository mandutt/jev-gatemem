## 1. 실행 주체 — A (core 내부 worker) 확정

### 1.1 3 AI 검토 결과 요약

| 항목 | a | b | c |
|---|---|---|---|
| 권장 | A (내부 worker + 모듈 분리) | A (내부 worker + 모듈 분리) | A (내부 worker + 모듈 분리) |
| B (cron) | ✗ 원칙 위배 | ✗ 원칙 위배 | ✗ 탈락 |
| C (가드 데몬) | ✗ 침묵 장애 위험 | ✗ 비용 > 이득 | ✗ 과설계 |

**공통 근거**:
- 재판정은 core 기존 책임(게이트 판정·상태 기록·pending 재처리)의 **연장선** — "미완료 게이트 판정의 최종 일관성 확보"
- `requeue_pending_gate` 60초 루프 패턴 **재사용** → 새 scheduler·IPC·supervisor 설계 불필요
- C는 프로세스 +1 → 로컬 환경에서 감독자 없는 **침묵의 장애 위험 2배** + SQLite coordination (lock, schema coupling) 문제 신규 발생
- SRP 우려는 "변경 이유가 같은가" 기준으로 **실질적 위반 아님** — 3인 모두 일치

### 1.2 모듈 구조 (a·c 제안 채택)

```
jev_mem_core/
  pipeline.py              # (기존) gate 호출, 상태 전이
  ledger.py                # (기존) 상태 머신, gate_outage
  workers/
    pending_gate_worker.py     # (기존) 60초 루프
    failopen_rejudge_worker.py # (신규) 재판정 worker — core 내부
  recovery/
    circuit_breaker.py         # (신규/이동) 회복 감지 상태
    outage_tracker.py          # (신규) incident 추적
```

- **process는 하나, worker 책임은 분리** — SRP 충족 + 운영 단순성 유지
- core는 주기적으로 `rejudge_worker.step()`을 1회 호출하는 host 역할만

## 2. 회복 감지 (D4, D7) — 브레이커 충돌 해결

### 2.1 문제 (b 신규 발견 ①)

서킷 브레이커가 open이면 호출 자체가 차단 → "실사용 3회 성공"이 **관측 불가능**.
402/403(fail-open 유지)은 문제없지만, `JevUnavailable`(TRANSIENT)로 브레이커가 열린 경우 회복을 영영 못 봄.

### 2.2 해결 (b 제안 채택)

```
circuit open 상태에서도 실제 요청 유입 시:
  └─ open 후 대기시간 경과 시 1건만 half-open 시험 통과 (실제 사용자 요청)
      ├─ 성공 → closed (회복 카운터 시작)
      └─ 실패 → open 유지 (다음 대기시간부터 재시도)
```

- **추가 호출 0 유지** (시험 통과는 실제 요청 자체)
- 브레이커 미사용 환경: 이 문제 없음 (fail-open이 계속 호출)

### 2.3 회복 판정 상태 (DB 영속화, b·c)

```
gate_outage 테이블 확장:
  recovery_success_count   — 연속 성공 횟수 (메모리 아님, 재시작 안전)
  recovery_confirmed_at    — N회 달성 시각
  rejudge_eligible_at      — confirmed_at + M분 (히스테리시스)
  rejudge_started_at       — worker가 실제 시작한 시각
```

### 2.4 성공 3회 증거력 (b 신규 발견 ③)

- 턴당 게이트 2회 호출(user/assistant) → 3회 연속 성공 ≈ **1.5턴**
- 해결: **"서로 다른 턴 기준"으로 정의** (같은 턴 내 2회는 1회로 카운트) + M분 조건 명시
- 혹은 하이브리드: `JEV_RECOVERY_STREAK=5` 등 환경변수로 조정 가능

## 3. 자동 재판정 worker (D1-D3, D5, D6)

### 3.1 worker 루프 (c 제안 — source of truth 기반)

```
[worker 시작/주기 호출] (60초, requeue와 병렬)
  └─ recovery state 확인 (eligible_at 도달?)
       └─ worker는 JEV 호출 없이 로컬 SQLite만 확인
  └─ SQLite = queue 겸용:
       WHERE preservation='quarantine'
         AND rejudge_status='pending'
         AND lease_until < now()
  └─ claim (lease_until = now + LOCK_SECONDS)
  └─ batch 재판정 (strict, batch size 제한, JEV 호출)
       ├─ KEEP   → 자동 승격 (rejudge_kept, 비파괴)
       ├─ SKIP   → staged (rejudge_skip_staged, recall 제외) — 최종 삭제는 수동 승인 (D4·v2 유지)
       └─ 실패   → rejudge_failed → 다음 주기 재시도 (lease 만료 시 pending 복구)
  └─ 결과 transaction commit + lease release
```

- **restart-safe**: worker 메모리에 진행 상태 없음, DB가 유일한 state → PC 재부팅에도 이어서 실행
- **idempotent**: lease 기반 claim이라 재실행 안전

### 3.2 JEV 호출 예산 (a·b·c 전원)

```
JEV concurrency budget
   ├─ foreground gate : priority HIGH (실시간 사용자 요청 보호)
   └─ rejudge worker   : priority LOW, bounded concurrency (예: max 1-2)
```

- **마이크로 배치**: 1회 루프당 3~5건 재판정 후 휴식 (a) — 실시간 요청 대역폭/크레딧 양보
- **토큰/크레딧 상한**: 실행당 건수 상한 → 초과분은 다음 주기로 이월 (b 신규 발견 ②)
- **재장애 시 즉시 중단**: BILLING/AUTH는 1회, TRANSIENT는 연속 N회 (D8)

### 3.3 하이브리드 트리거 (a·b)

```
같은 엔진 함수 (failopen_rejudge_worker.step / run_batch)
  ├─ 내부 루프 (기본 ON, JEV_AUTO_REJUDGE=0이면 OFF)
  ├─ CLI 수동 (기존 jed_failopen_rejudge_v2.py → 이 모듈 import)
  └─ admin 엔드포인트 (선택, POST /v1/admin/rejudge/run — 멱등, lease 보호)
```

- 자동·수동 판정 로직 **분기 없음** — 외부 cron을 쓰고 싶은 사람만 같은 엔드포인트 호출

## 4. 실패 격리·킬 스위치 (b)

- **exception boundary**: 재판정 루프의 버그가 core 전체를 죽이지 않게 태스크를 예외 경계로 감쌈 → 죽어도 core는 살아있고, 연속 실패 시 스스로 비활성화
- **킬 스위치**: `JEV_AUTO_REJUDGE=0` → 즉시 중단 (수동 도구만 동작)
- **SQLite 쓰기 경합**: 배치 커밋을 작게 쪼개 writer 점유 시간 최소화

## 5. staged SKIP 방치 방지 (b 신규 발견 ④)

알림 없는 설계에서 승인 대기 건이 쌓여도 무감지 (이번 35시간 장애 방치와 같은 구조).

```
/v1/status + 응답 필드에 노출 (경량 원칙 유지, 별도 인프라 없음):
  rejudge: {
    pending: n,           — 재판정 대기
    skip_staged: n,       — 승인 대기 (SKIP 후보)
    oldest_staged_days: n — 최고령 승인 대기 일수
  }
```

- 에이전트가 읽는 응답 필드에도 요약 포함 → 일정 기간 지나면 눈에 띄게
- 사용자가 몰라서 방치되는 상황 방지
