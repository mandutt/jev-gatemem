# 장문 메모리 후속 작업 재검토 요청 — 3종 AI 검토 반영 이후 (stage10~22)

- **작성일**: 2026-10-05
- **검토 대상**: jev-memory-middleware (JEV 기반 메모리 게이트웨이, **jev-mem**)의 장문 메모리 회수 문제 — 1차 검토(3종 AI) 이후 진행된 후속 작업 전체
- **검토 의뢰 사유**: 1차 검토의 지적 15건 중 13건을 처리(실측/반영/기각)했고, 적용 3건을 운영 반영했다. **이후 결정들이 타당한지, 놓친 게 없는지 최종 검증**이 필요하다.
- **중요 전제**: `jev-mem`은 arXiv 2609.23986의 학술 프로젝트 "Jev-Mem"과 **이름만 유사한 별개 프로젝트**다.

---

## 1. 한 문단 요약

1차 검토에서 지적된 "실측 4 벡터 순위 이상(sanity 검사)"을 실행하던 중 **치명적 하네스 버그**를 발견했다: 실험 스크립트의 직접 `TextEmbedding()` 호출이 운영 모델(bekko-a8m)이 아닌 **bge-small-en-v1.5로 폴백**해, stage1c/3의 벡터 실측 전부가 잘못된 모델로 측정됐었다. 정확한 모델로 재실측하자 "청크 벡터가 상위로 못 간다"는 결론이 **역전**(chunk rank≤2: 0→10건)됐다. 이를 바탕으로 c-ai가 추천한 **parent multi-vector(late chunk retrieval)**를 0콜 파일럿으로 검증했으나 **통합 이득 0으로 기각**됐다(이유: [ASSISTANT] 제외 해제 후 gold 부모는 이미 FTS/vec로 풀에 존재). 이후 기저율이 98%임을 확인하고, **POOL_BUDGET 40→60**과 **답 구간 발췌(snippet 윈도우)** 2건을 추가 채택·운영 반영했다. 최종적으로: **적용 3건([ASSISTANT] 제외 해제, POOL_BUDGET 60, snippet 윈도우), 기각 4건(저장 청킹, chunkmax, parent multi-vector, 사이드카 FTS 레인)** 으로 수렴했다.

## 2. 시스템 개요 (jev-mem, 1차 요청서와 동일)

- 메모리: SQLite 행 단위(`working_memory` 1,673 / `episodic_memory` 113). 임베딩 bekko-a8m 384차원 (working은 `memory_embeddings` JSON + `vec_working` vec0, **episodic은 `vec_episodes` vec0에만 존재** — S4 설계).
- 읽기 파이프라인 (쿼리당): lane pool(FTS 60 + vec 60 + importance 8 + graph 10, RRF) → 어휘 게이트(`_filter_and_rank`, **현행 min_distinctive=2, min_coverage=0.30**, vec rank≤2 예외) → **POOL_BUDGET=60**(2026-10-05 40→60) → Jev choice 1콜(라벨 = 후보당 100자 excerpt) + abstain → lift.
- 쓰기: 발화별 Jev 게이트 → KEEP 시 행 저장 (장문도 1행).
- **적용 변경 1**: `_PREFETCH_EXCLUDED_PREFIXES = ()` ([ASSISTANT] 프리픽스 행의 prefetch 제외 해제, 커밋 `ffb2ca5`).
- **적용 변경 2**: `POOL_BUDGET = 60` + `POOL_DEFAULT_TOP = 60` + **RPC 경로(`jev_mem_core/pipeline.py`)의 컷 누락 수정** (`filtered[:POOL_BUDGET]` 명시 — 이전엔 컷 없이 전부 Jev에 전송), `gateway.py` 기본 budget 60 (커밋 `1e32a95`).
- **적용 변경 3**: `jev_rerank` 라벨 생성 — **장문(>800자) 행만** `_query_window`(쿼리 인지 300자 윈도우→150 excerpt) 사용, 단문은 head-100 유지 (커밋 `513bdba`).

## 4. 후속 실측 전체 (stage10~22, 전부 0콜 또는 무료 레인 소량)

### ① 하네스 버그 (stage10) ★
직접 `TextEmbedding()`이 `BAAI/bge-small-en-v1.5` 로드 (sitecustomize의 `MNEMOSYNE_EMBEDDING_MODEL=bench/bekko-a8m` 강제는 beam 경로에만 적용). 같은 문장 fastembed vs beam cosine ≈ 0.02로 확인. → stage1b/1c/3의 벡터 실측은 bge-small로 돈 것 → **"chunk rank≤2=0건" 무효**.

### ② 정확 모델 재실측 + parent multi-vector (stage10b~12)
- 정확 모델(bekko-a8m): gold 19 whole rank median 400~1,600→**107**, chunk rank≤2 **0→10건** (역전).
- stage11: 227청크 sidecar, 쿼리-vs-청크 max collapse → chunk-lane 단독 top-5 11/19, top-19 18/19 (whole 5/19 대비 +13).
- **stage12: 실제 파이프라인에 5번째 레인으로 통합 → gold pool 15/19 그대로, gate 8/19 그대로, op-90 회귀 0, noans 0. 이득 0 → 기각.** 이유: [ASSISTANT] 해제 후 gold 부모는 이미 FTS/vec로 풀에 존재 → 청크 레인은 중복.

### ③ 기저율 (stage16)
query_log 115건 중 비기계 87건: 장문(plain >1,350자 136행)이 **pool 87/87(100%), gate 통과 85/87(98%)**, **top-1 0/87**. → 장문 노출은 보편적, **진짜 갭 = "gate까지 오지만 Jev가 top-1로 안 고름"**(head 절단 의심).

### ④ 답 구간 발췌 / snippet 윈도우 (stage17~18) ★채택
`_query_window`: 본문에서 쿼리와 어휘 겹침이 최대인 300자 구간을 50자 스텝으로 탐색 → 150자 excerpt. **장문(>800자)에만 적용, 단문은 head-100 유지** (부분 반영).

| 지표 | baseline (head-100) | snippet |
|---|---|---|
| gold 12건 lift (2회) | 6/24 | **10/24 (+2)** |
| 손실 | — | 0건 |
| op-90 서브셋(40) gold-pick | — | 개선 1, 회귀 0 |
| noans 6건 | — | 변화 0 |

- 새로 lift된 gold 2건(0e63e2c7, 05ab2f73) 모두 장문, head-100으론 못 고르던 것.
- **부분 반영이 전면 반영과 동일 효과** (단문은 head가 이미 본문 대부분 커버).

### ⑤ CI + exact McNemar (stage21)
| 수치 | Wilson 95% CI |
|---|---|
| gold 1/19 (제외 전) | [0.9%, 24.6%] |
| gold 8/19 (제외 해제) | [23.1%, 63.7%] |

### ⑥ POOL_BUDGET 스윕 + Jev lift 실측 (stage13~15) ★채택
- stage13: 잔여 탈락 7건 = "게이트 통과는 하나 top-40 랭크 컷"(gate_rank 44~104). POOL-MISS 4건은 구조적 한계.
- stage14: 컷 40/50/60/80/100 → gold gate 8/11/12/13/14, **op-90 회귀 0, noans 0 전 구간**.
- stage15 (무료 레인): **Jev 실제 lift = 게이트 통과 ≠ 선택**. cut 60에서 1/6건만 lift(97bca6e2), **cut 80/100은 abstain 폭증으로 전멸(NO-PICK)** → **60이 실질 상한**.
- 토큰: 40→60 = +50% (쿼리당 ~+1,360토큰, 연간 ~$11~22 무시 가능), 콜 수 불변.

### ⑦ episodic 벡터 (stage19)
"벡터 없는 장문 8행" → episodic 113행 전부 memory_embeddings에 없으나 **vec_episodes(vec0)에 113행 전부 존재** — S4 설계("episodic은 vec_episodes에만 존재, 재임베딩 제외"). 정상, 누락 아님. 교훈: 임베딩 진단은 vec_* 포함.

### ⑧ 사이드카 FTS 레인 (stage22) ★기각
청크 전용 FTS5(227청크) 5번째 레인: gold 12/19 그대로, op-90 회귀 0, noans 0 → **이득 0** (stage12와 동일 이유).

## 6. 검토 쟁점

**쟁점 1 — 적용 3건(제외 해제 + POOL_BUDGET 60 + snippet)이 정합적인가?**
각각 독립 실측으로 채택됐는데, **3건의 상호작용**(예: snippet이 gate 통과 행에만 적용되므로 POOL_BUDGET이 먼저 풀어야 의미가 있음)을 고려할 때 조합이 최적인가? 하나를 빼면 어떤 영향?

**쟁점 2 — 기각 4건(저장 청킹, chunkmax, parent multi-vector, 사이드카 FTS)의 실측이 충분한가?**
특히 parent multi-vector는 "통합 이득 0"으로 기각했는데, **gold 19의 4건 POOL-MISS(afd156a9, 329fb315, f66a777d, 77f9a2b2)를 살릴 수 있는 유일한 경로**일 수 있다. 이 4건(전체의 21%)을 포기하는 게 맞는가? 단축행 통제 미실시(쿼리 특성 vs 길이 원인 미분리)가 이 판정을 흔드는가?

**쟁점 3 — breach: "게이트 통과 ≠ Jev lift" (stage15)가 남긴 문제**
cut 60에서 gold 12건 중 Jev가 실제 lift한 건 3건뿐이었다(stage17/18 baseline 6/24=3건 환산). **나머지 9건은 게이트를 통과해도 Jev가 다른 후보를 고른다.** 이건 "choice 프롬프트"의 문제인가, "중복·유사 후보가 많은 풀"의 문제인가, 아니면 gold 자체가 Jev 판정 기준과 안 맞는 것인가? 이 갭을 좁힐 저비용 방법이 있나? (winner gate R2 결합, 라벨 포맷, instructions 등)

**쟁점 4 — snippet 윈도우의 일반화**
- 윈도우 스캔은 쿼리-어휘 겹침 기반인데, **완전 의역 쿼리(겹침 0)**에는 윈도우가 head로 폴백한다 — 효과 없음. 이 한계를 벡터 유사도 윈도우로 바꾸면 나아질까? (비용: 임베딩 60회/쿼리 추가)
- 장문 중 **답이 여러 구간에 분산**된 경우 300자 윈도우 1개로 부족할 수 있다. 복수 윈도우가 나을까?

**쟁점 5 — [ASSISTANT] 제외 해제의 장기 리스크**
op-90/noans 실측에선 회귀 0이었지만, **어시스턴트 발화 노이즈가 실사용에서 prefetch 컨텍스트를 오염**시킬 리스크는 남아 있다. 어떤 모니터링 지표로 이걸 조기 감지할 수 있나? (예: prefetch 평균 토큰, assistant 행 비중, noans abstain율)

**쟁점 6 — 더 해야 할 실측이 있나?**
- winner gate(800자 head 캡)에 snippet 윈도우 적용 — 게이트 판정 규칙 변경이라 shadow 후로 미뤘는데, 지금 할 가치가 있나?
- op-90 회귀가 "gate pass" 기준이라 "실제 hit@3(최종 컨텍스트)" 변화는 아직 미측정. 최종 지표로 한 번 더 확인할 가치가 있나?

## 7. 의뢰자 성향 (반대 의견 환영)

- **"채택은 실측 후"** 원칙. 0콜/무료 레인 실측 선호. 비용·콜 수 증가 강하게 꺼림.
- 최소 변경 선호 (적용 3건 모두 코드 1~2줄 수준).
- **반박·기각 지적을 환영**한다. 특히 "적용 3건 중 하나는 과했다"는 의견과 근거를 정직하게 제시해 달라.
