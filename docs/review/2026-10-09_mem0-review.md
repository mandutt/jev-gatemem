## 아티클 요약 (mem0의 기술 주장)

1. **"메모리 결정은 문장을 쓰는 LLM이 필요 없다"** — Jev(System One) 같은 typed classifier가
   yes/no·라벨·점수 판정을, 시스템 2(LLM)는 최종 답변 작성만.
2. **typed + batched + bounded questions** — 작은 출력 공간이므로 파싱 불필요, 같은 state 공유 질문은 1회 배치.
3. **write path / read path 도식** — 모든 메모리 시스템의 3단계(쓰기·검색·LLM 답변) 중 중간 결정을 Jev로 이동.
4. **경고: thresholds 미보정** — "0.95 cutoff는 0.95가 항상 같은 의미일 때만 의미 있다". 부록이
   "returned values are not assumed to be calibrated probabilities"라고 명시. 단일 모델·단일 벤치마크(LoCoMo)로만 평가.
5. **루프 캡**: depth 8 / 60 visited nodes / 16 controller calls / 15초 — 무한 루프 방지.
6. **mem0 적용 예시**: `client.search()` 결과에 relevance classifier 필터를 끼우는 코드 스니펫
   (`THRESHOLD = 0.5 # placeholder: tune on your own labeled queries`).
7. **timestamps 강조**: additive 경로에서 옛·새 사실이 둘 다 나오므로 timestamp로 최신 버전 판별.

## 유일한 미검토 축: "timestamp 노출" — 0콜 DB 프로브로 실측, 불필요 판정

mem0의 timestamps 포인트는 **additive 스토어에서 옛+새 사실이 둘 다 검색에 뜨는 문제**다.
우리는 write-time supersede/valid_until + read-time 필터로 이미 차단하고 있다는 것을
**실제 코퍼스로 확인**했다 (0콜, 코드 미변경):

- **프로브**: `experiments/operational-golden/mem0_timestamp_probe.py` 실행 로그 `mem0_probe_run.log`
- **결과 (mnemosyne.db 2,085행)**:
  - superseded 113건·valid_until 159건 — supersede 메커니즘이 실재하며 동작 중
  - 정확 content 중복 15그룹(x2~x8) — 전부 **작업 지시·이벤트 반복**(statem-bench 프롬프트, codex session resume,
    `[IMPORTANT: Background process]` 통지) — "같은 사실의 구버전·신버전 충돌"이 아님
  - 명사 클러스터(50%+ 겹침) 99그룹 — 마찬가지로 이벤트 반복·세션 재개 프롬프트가 대부분
- **판정**: mem0의 additive 시나리오가 우리 코퍼스에 실질 발생하지 않음 → Jev 라벨/헤더에 timestamp를
  추가해도 해결할 문제가 없음 (토큰만 증가, 라벨 문구는 stage44/45에서 민감 — 라벨 변경은 재실험 대상)

## 기각

1. **relevance-score 필터 (mem0 코드 스니펫)** — 우리 stage50 Noul pointwise와 동일 레버, 실측 기각.
   do not re-run.
2. **timestamp를 Jev 입력에 추가** — 위 프로브로 불필요 확인. (코퍼스가 크게 변하면 재검토 여지 — 단
   그때도 라벨 문구 변경은 stage44/45 실측으로 재실험 필요.)
3. **"0.95 threshold" 류 하드 임계값** — 우리 stage100 'JEV score-floor 절대 임계값 금지'와 동일 교훈.
   기각 원칙 재확인일 뿐 새로울 것 없음.

## 결론

직접 반영할 코드·설계 없음. mem0 아티클의 모든 레버(typed/batched 결정·자기 데이터 보정·read-time
필터·timestamp)는 우리가 이미 실측·구현·기각 중 하나로 커버되어 있다. 아티클의 'threshold는
calibration이 핵심' 경고는 우리 canary drift 감시 설계가 이미 실현한 것. mem0의 additive 우려는
우리 코퍼스에서 실제 발생하지 않음을 0콜로 확인 — **보류 목록에 등록할 것도 없음** (기각 목록으로 종결).
