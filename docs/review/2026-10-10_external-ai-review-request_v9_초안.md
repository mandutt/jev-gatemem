## 2. 신규 실측: 판정 모델(haiku) κ — 1차 0.355 → 2차 확장 통합 0.157 (STAGE121/122)

### 배경
- 판정 표준인 claude-haiku-5.5:free의 **신뢰도가 검증된 적 없음** (b-ai: "품질 우수는 아직 숫자가 없다")
- 사람 라벨 보정 셋 2회 구축: 1차 46건(stage102p·deepcombo 응답) + 2차 54건(stage104·haiku 응답, no 16 과대표집)
- 응답 원문 전문 표시, 생성 실패분 DB에서 대체
- 사용자 직접 판정 (2클래스: "사용자 고유 정보 구체적 인용 여부")

### 1차 결과 (46건, STAGE121)

| 지표 | 값 |
|---|---|
| 일치율 | 87% (40/46) |
| **Cohen's κ** | **0.355** (95% CI [0.000, 0.727]) |
| 사용자 분포 | yes 44 (96%) / no 2 (4%) |
| haiku 분포 | yes 38 (83%) / no 8 (17%) |

불일치 6건 전부 haiku=no, 사용자=yes (Mnemosyne repo·commit governance·evidence 규칙·감사 보고서·리뷰 산출물·리뷰 전용 턴)

### 2차 결과 (54건 → dedupe 45건, STAGE122)

| 지표 | 값 |
|---|---|
| 시트 구성 | no 16 전부 + yes 38 (κ 정밀 측정용) |
| **사용자 판정** | **전부 yes (54/54)** |
| (query,sample) dedupe | 45건 (중복 9건 제거 — framing만 다른 동일 응답) |
| dedupe 후 일치 | 34/45 = 76% |
| **dedupe 후 κ** | **0.000** (사용자 yes 100% → 우연 일치로 계산) |

### 통합 κ (91건 = 46 + 45)

| 셋 | n | 일치 | κ |
|---|---|---|---|
| 1차 (deepcombo 응답) | 46 | 87% | 0.355 |
| 2차 (haiku 응답, dedupe) | 45 | 76% | 0.000 |
| **통합** | **91** | 81% | **0.157** |

- 통합 분포: haiku no 19 / yes 72 · 사용자 no 2 / yes 89
- **불일치 17건 전부 haiku=no → 사용자=yes** — 과소판정 편향 100% 단일 방향

### 핵심 해석

1. **haiku의 no 판정은 실질적으로 전수 오판** — 2차 셋(no 16건 전수 포함)에서 사용자가 1건도 no로 안 봄
2. **κ=0.157 (통합) = "거의 일치 없음"** — 1차 0.355는 no 2건이 희석시킨 과대값
3. **사용자 기준 k=5 fF no율(2.9%)은 사실상 0에 가까울 것**
4. **stage104(p=0.0078)은 완전히 신뢰 불가** — 이 셋의 no 16건 전부가 사용자 기준 yes였으므로
   "fT가 fF보다 no 많음(12 vs 4)"은 **haiku의 오판 분포일 뿐** 프레이밍 효과가 아님
5. **교훈**: 라벨링 시트 생성 시 (query,sample) dedupe 사전 적용 — 같은 응답을 2번 물으면 κ가 부풀림

### ★ 구체 사례: "스킬 만들 때 file_content로 보내면 돼?" (κ 편향의 메커니즘)

**질문**: Hermes의 skill_manage 도구 문법을 묻는 질문. 응답 원문:
> "아니요, `file_content`로 보내시면 안 됩니다. `content` 파라미터로 보내야 합니다. `file_content`로 보내면 계속 'content is required' 오류가 발생합니다."

**판정 프롬프트에 Hermes/에이전트 정보는 없음** (순수 user 메시지 — 시스템 정보 미주입).
→ haiku는 "이 에이전트가 Hermes다"를 모른 채 판정.

**haiku 판정이 k에 따라 갈림**:
| 조건 | haiku | 이유 |
|---|---|---|
| k=2 | **no** (3/3) | "파라미터 이름·오류 메시지는 일반적 도구 사용법" |
| k=3 | yes 3 / no 2 | "과거 실패 이력 인용" vs "일반 파라미터 규칙" |
| k=5 | **yes** (5/6) | "content is required 오류 반복 — 과거 이력 인용" |

**해석**: 이 답변("file_content vs content" + "content is required 오류")은 **Hermes skill_manage의 과거 실패 이력이 메모리에 있어야만 나올 수 있는 내용**.
haiku가 Hermes를 모른다면 **메모리 인용(yes)으로 판정해야 맞음**. 헤르메스 지식이 없는 haiku가 "일반 API 지식"으로 치부한 것 = **κ=0.355 과소판정 편향의 직접적 실례**.
k=5에서 yes로 바뀌는 건 **메모리 5개 노출 시 응답에 과거 이력이 더 풍부해져** haiku가 알아챈 것 — **노출 k가 판정에 영향을 줌**.

**3축 설계에 대한 함정**: 축1("메모리 없이도 알 수 있나?")도 haiku가 "Hermes tool 사용법 = 일반 지식"으로 보는 한 **같은 오판을 반복**한다.
→ **"사용자 고유 정보 vs 플랫폼(에이전트) 공개 지식"의 경계 정의가 3축 설계의 전제 조건**이라는 것이 이 사례로 입증됨 (Q1에 반영)

### 시사점
1. **haiku 판정을 골드로 신뢰 불가** — κ=0.355 "약한 일치", CI 상한 0.73
2. **stage104(p=0.0078) 신뢰도 추가 약화** — haiku의 no 과소판정 편향이 프레이밍 차이로 읽혔을 수 있음
3. **k=5 fF no율 2.9%는 사용자 기준에선 더 낮을 것** — haiku가 no를 과다 생성하므로

## 3. 신규 설계: 판정 기준 3축 (v9 검토 대상)

> 배경: 예시 추가(파일 경로·설정 값 등)는 **도메인 오버핏** — 코딩 도메인 예시를 넣으면 다음 도메인에서 또 틀림 (stage64~66 교훈: '분야 키워드 분류기' 기각 → 도메인 무관 기준 채택)

### 축 1: "일반 지식 대체 가능성" 기준 재정의
- 판정 질문: "사용자 고유 정보를 인용했나?" → **"이 응답의 핵심 정보를 메모리 없이(일반 지식/추론으로)도 얻을 수 있었나?"**
- no = 메모리 없이도 답할 수 있는 내용뿐 (일반 지식 대체 가능)
- yes = 메모리가 없으면 알 수 없는 내용 포함 (사용자 특정)
- 예시 목록은 "기준의 정의"가 아니라 판정 보조 도구로만

### 축 2: no 판정만 2차 검증 (비용 최소화)
- no는 희귀 클래스 (운영 k=5 fF no 2.9%) → **no만 재검토** = 전체의 ~4%만 추가 비용
- 2차 검증 = 축 1 재질문 + (필요 시) 사람 확인

### 축 3: "구체성 신호" 규칙 스크리닝 (도메인 무관 regex)

| 신호 | regex 예 | 비고 |
|---|---|---|
| 경로 | `[A-Za-z]:\\...` · `/.../...` | OS·프로젝트 무관 |
| URL | `https?://...` | 코드·문서·웹 |
| 숫자+단위 | `\d+%` · `\d+(\.\d+)?(초\|분\|시간\|ms)` | 실험·성능·벤치 |
| 버전/해시 | `v?\d+\.\d+\.\d+` · `[0-9a-f]{7,}` | 코드·패키지·커밋 |
| 고유명사 | `[A-Z][a-z]+( [A-Z][a-z]+)+` | 제품·모델·도구 (영문) |
| 키-값 설정 | `\w+=\w+` · `key: value` | config |

- 용도: haiku=no + 신호 있음 → "no 의심" 플래그 (자동 재검토 트리거)
- 한계: 텍스트형 인용(규칙 문구·원칙)은 신호가 없을 수 있음 → 축 1이 커버
- 역할: "의심 증폭기" — 판정 대체가 아니라 1차 검증의 보조

### 결합 동작
```
haiku 판정
  ├─ yes → 통과 (희귀 클래스 no만 검증하므로 yes는 신뢰)
  └─ no ─→ [축1] "일반 지식 대체 가능?" 재질문
            └─ [축3] 동시에 "구체성 신호" 스캔
                 ├─ 신호 있음 → no 의심 → 재판정 우선
                 └─ 신호 없음 → no 유지
```

### 검증 계획 (stage118 완료 후)
1. 기존 46건 라벨에 축 3 스크리너 적용 → "신호 있음→사용자 yes" **재현율** (6건 중 몇 건?)
2. "신호 있음→사용자 no" **오탐** (no 2건이 신호에 걸리면 정밀도 낮음 명시)
3. 재현율·정밀도 충분 → haiku 파이프라인에 "no + 신호 → 재검토" 단계 추가
4. **κ 재계산: 사람 라벨 46→100건으로 확장 후 측정** (재판정만으로는 yes 오판을 못 잡음)
