# 장문 메모리 청킹(chunking) — 검토 요청: "mid-답 회수 불가" 문제의 해결 경로

- **작성일**: 2026-10-05
- **검토 대상**: jev-memory-middleware (JEV 기반 메모리 게이트웨이, 이하 **jev-mem**)의 장문 메모리 회수 문제
- **검토 의뢰 사유**: 가설 → 3종 실측 → 전부 기각. "문제가 실제로 있는가"는 확인됐으나 "해결 가능한가"는 미해결. 해결 경로가 정말 없는지, 놓친 접근이 있는지 외부 관점 검토 필요.
- **중요 전제**: 여기서 다루는 `jev-mem`은 arXiv 2609.23986의 학술 프로젝트 "Jev-Mem"과 **이름만 유사한 별개 프로젝트**입니다. 혼동하지 말 것.

---

## 1. 한 문단 요약

최근 게시물(supermemory, DhravyaShah)이 "Jev(결정형 LLM 판정 API)를 **문장별 continuation 판정으로 문서를 청크**하는 데 쓰면 chunking SOTA"라고 주장했다. 우리 시스템(jev-mem)은 메모리를 행 단위로 저장·검색하는데, 실측 결과 **"답이 장문 메모리의 중간(mid)에 있는 쿼리"는 현행 검색 파이프라인이 사실상 회수하지 못한다(gate 통과 5.3%)**는 문제가 확인됐다. 이에 ① Jev chunking ② 규칙 기반 800자 저장 청킹 ③ 게이트 입력만 청크로 계산 — 3가지 해법을 0콜(무료) 실측으로 검증했고 **전부 기각**됐다. 남은 유일한 경로(이중 저장)는 이득이 1건 규모로 비실용적이다. **"문제는 실재하지만 청킹 류 설계로는 해결 불가"가 현재 결론.** 이 결론이 타당한지, 놓친 접근이 있는지 검토받고자 한다.

## 2. 시스템 개요 (jev-mem)

- 메모리 저장: SQLite 행 단위 (`working_memory`/`episodic_memory`), 행당 content(발화·보고서·분석 결과) + 임베딩 벡터(bekko-a8m, 384차원, 512토큰 clamp) + FTS5 인덱스.
- 읽기 파이프라인 (쿼리당):
  1. **lane pool**: FTS(60) + vec(60) + importance + graph → RRF 병합 → 풀 형성
  2. **어휘 게이트** (`_filter_and_rank`): min_distinctive=2 (쿼리-행 content 토큰 교집합 ≥2), min_coverage=0.30 (교집합/쿼리토큰 ≥30%). 단 **vec rank ≤2** 행은 예외 통과.
  3. **POOL_BUDGET=40** 후 **Jev choice 1콜** rerank (1위 lift). abstain 라벨로 무답 거부.
- 쓰기: 발화별 Jev 게이트 → KEEP 시 행 저장. 장문도 **한 행**으로 저장 (분할 없음).
- 규모: working 1,625 + episodic 113 = 1,738행. 전체의 11.3%(197행)가 1,350자 초과, 최대 107,885자.
- 관련 이전 판정들: "완전 의역 쿼리는 vec lane으로 회수 불가" (Run M, 2026-10-01, 임베딩 모델 교체 외 해결책 없음으로 종결).

## 3. 당초 가정 (검토 트리거)

게시물 주장: Jev로 문장별 continuation(yes/no) 판정 → 문장 경계를 넘어선 곳에 청크 경계 → **의미 단위 청킹 SOTA**. 우리에 적용하면:
- (가설 A) 장문 메모리는 full-text 게이트 800자 절단에 답이 잘려 NO 판정 (절단 손실)
- (가설 B) 512토큰 clamp 통째 임베딩은 벡터가 희석 → vec lane 회수 불량 (벡터 희석)

### 실측 5/6 — 실제 파이프라인 스크래치 (청크 저장 vs 현행)
라이브 DB 사본 2개(현행 vs 장문 48행 → 223 청크행, FTS/vec0 재구축)를 **실제 lane pool+게이트**로 실행.

**자기발췌 mid-query 48건:**
| 지표 | 현행 | 청크 저장 |
|---|---|---|
| pool hit | 41/48 | 41/48 |

**실사용 gold 19건 (아래 §5):**
| 지표 | 현행 | 청크 저장 |
|---|---|---|

→ 저장 청킹은 게이트를 살리지만 **vec lane에서 5건 손실** (청크 벡터가 풀 상위에 못 들어감).

### 실측 7 — "게이트 입력만 청크" 파일럿 (행 유지 + `_filter_and_rank` 어휘 겹침을 800자 청크별 max로)
| 지표 | 현행 게이트 | chunkmax 게이트 |
|---|---|---|
| 실사용 gold 19 gate pass | 1/19 | **1/19 (개선 0)** |
| op 90 회귀 (gate pass) | 81/90 | 81/90 (손실 0) |

**원인 분해 (gold 19 벡터 rank)**: whole rank ≤2(예외로 살릴 수 있는) = **1건**, chunk rank ≤2 = **0건**, 대부분 rank 400~1,600.
→ 이전 저장-청킹이 8/19 통과한 것은 "청크 벡터가 상위"가 아니라 **청크 행이 풀에 대량 진입해 어휘로 통과**한 것. 행을 유지한 채 게이트만 바꾸면 개선 0.

## 5. 실사용 gold 19건 (사람 판정)

query_log 83건 + 장문 행 출처 세션 transcripts의 사용자 실제 질문에서 후보 155건 → 행별 최적 쿼리 38건을 **사용자가 직접 판정** (VALID: 행이 답을 포함 / PLAUS / IRREL + 답이 mid 40~60% 존재 여부). **VALID+mid=YES 19건**을 gold로 확정. (idx 21 1건은 에이전트 재검토로 PLAUS→VALID 교정, 사용자 승인)

## 6. 검토 쟁점

**쟁점 1 — "청킹 류 설계 전부 기각" 판정의 타당성.**
3종(①②③)이 각각 pool 손실/개선 0으로 기각된 실측은 충분한가? (특히 ③은 op 90 회귀 0이면서 gold 개선 0 — "게이트만 바꿔선 안 된다"의 증거가 맞나?)

**쟁점 2 — 남은 유일 경로 "이중 저장(행 + 청크 행)" 채택 가치.**
이득이 rank≤2 1건 규모(실측 7)로 비실용적이라는 판단이 맞나? 아니면 프리즘(중요도/최신성) 등을 고려하면 이득이 더 큰가? (이중 저장 = 쓰기 2행 + FTS/vec 재구축 + 읽기 병합, 마이그레이션 부담)

**쟁점 3 — 놓친 접근이 있는가.**
- 청킹이 아닌 "장문 전용 처리": prefetch 반환 시 본문에서 **답 후보 구간을 발췌**해 주입 (게이트는 행 단위 그대로, 출력만 청크 발췌) — 이건 시도 안 했는데 가치가 있나?
- **쿼리 확장(Doc2Query 역방향)**: 장문 행에 대해 "이 행이 답이 될 질문"을 생성해 FTS/vec에 추가 — 단 Run P/Q에서 "대화 도메인은 질문 생성 불가"로 기각된 적 있음. 장문(보고서) 도메인에서는 다를까?
- **임베딩 모델 교체** (벡터 lane 재구축) — 이미 Run M에서 종결됐지만, 장문 mid-답 한정으로 다시 열 가치가 있나?
- 그 외 우리가 안 본 접근.

**쟁점 4 — 실측 설계의 허점.**
- 자기발췌 mid-query(실측 3~5)는 실제 쿼리 분포와 다를 수 있다. 실사용 gold(실측 6)로 보정했는데, gold 19건이 "행의 출처 세션에서 나온 질문"이라 **편향**(그 세션 문맥을 아는 질문)이 있을 수 있다. 이 편향이 결론에 영향을 주는가?
- 쿼리 19건 중 다수는 길고 도메인 특화적(예: "S4 임베딩 마이그레이션 이후 다른 에이전트 경로 검증") — 실제 회수 실패가 "장문" 때문인지 "쿼리 특성" 때문인지 분리됐나?

## 7. 의뢰자 성향 (반대 의견 환영)

- "**채택은 실측 후**" 원칙. 0콜 실측으로 판정하는 것을 선호. 비용·콜 수 증가는 강하게 꺼림.
- 현재 **"청킹은 끝났다"**에 기울지만, "장문 보고서를 입력하면 회수가 안 된다"는 사용자 가설이 실측으로 확인된 이상 **무언가 해야 한다는 압박**도 있음.
- 이중 저장·마이그레이션은 Docker 같은 무거운 해법과 함께 비선호. 최소 변경을 원함.
- **반박·기각 의견을 환영한다.** "기각이 성급하다"는 지적과 근거를 정직하게 제시해 달라.

## 8. 요청 사항

1. 쟁점 1~4 각각에 대한 판정 + 근거 (간결).
2. "우리가 놓친, 0콜 또는 저비용으로 시도할 가치가 있는" 접근이 있다면 구체적으로 (실험 설계 포함).
3. 만약 "이중 저장" 또는 다른 접근을 권한다면, **최소 변경**으로 검증 가능한 파일럿 설계를 제안해 달라.
4. 결론적으로: 이 문제를 "닫을" 것인지, 특정 경로로 "계속 팔로우업"할 것인지.
