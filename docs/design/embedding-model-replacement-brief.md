# 임베딩 모델 교체 검토 의뢰서 (2026-09-30)

> 이 문서는 외부 AI에게 **소형 로컬 임베딩 모델 후보 확정**을 의뢰하기 위한 것입니다.
> 별도 자료 없이 이 문서만으로 맥락 파악이 가능하도록 작성되었습니다.

---

## 1. 시스템 개요

**Mnemosyne**이라는 로컬 에이전트 장기기억 시스템을 사용 중입니다. 핵심 구성:

- **저장소**: SQLite (WAL) + sqlite-vec (int8 양자화 벡터 컬럼)
- **회수(recall)**: 4레인 하이브리드 — FTS(키워드 전문검색) + **vec(벡터 유사도)** + importance + graph 인접
- vec 레인 가중치: `vec_weight: 0.5` (기본값)
- **런타임**: Python 3.14 전용 venv, **fastembed 0.8.0** (ONNX 기반 로컬 추론), sqlite-vec 0.1.9
- **완전 로컬 설계**: 임베딩 API 호출 금지 (오프라인·프라이버시·비용 이유로 로컬 ONNX 추론이 하드 요구사항)
- **하드웨어**: Windows 11, CPU 전용 (GPU 없음), **RAM 15.6GB (메모리 압박에 민감)**, NVMe SSD

### 현재 임베딩 모델

- `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` (2021년, 118M params, 384차원)
- 구성에서 `embedding_dim: 384`, `vec_type: int8`
- 실측: 프로세스 WorkingSet ~124MB, Private commit ~975MB (fastembed+ONNX 런타임 포함)
- 추론 지연 실측: p50 276ms / p95 453ms (쿼리 1건 기준, 예산 1.5s)

### 구조적 특수사항

- 멀티에이전트 아키텍처: 여러 코딩 에이전트(Hermes/Codex/pi/OpenCode)가 하나의 **core 데몬(HTTP, 싱글턴)**을 통해 메모리에 접근. 임베딩 모델은 **데몬에서 단 1회만 로드**됨 → 모델 교체는 이 데몬에서만 하면 됨
- 기존 기억 데이터(수천 행)가 384차원 벡터로 이미 저장되어 있음 → **모델 교체 시 전량 재임베딩 필요** (토글이 아니라 일회성 마이그레이션 비용)
- 교체 검증 시 사용 가능한 회귀 골드: 대표 쿼리 50개 (현재 게이트/회수 품질 F1 0.829 기준선)

## 2. 사용 패턴 (성능 요구사항 결정에 중요)

- 텍스트: **한국어·영어 혼용** (한국어 비중 높음). 기억 내용은 코딩 세션 대화, 기술 노트, 사용자 선호도, 실험 결과 등
- 쿼리: 자연어 질문이나 최근 대화 발췌 → 유사 기억 회수. 문서 길이는 수십~수천 자 (짧은 편)
- 호출 빈도: 에이전트 턴당 1~2회 (저장 1 + 회수 1). 동시 4~8 클라이언트
- **지연 예산: 회수 전체 1.5s / 상한 2.0s** (임베딩이 이 안에 들어야 함 — 현재 p95 453ms로 여유 있음)
- 처리량 요구는 낮음 (docs/s 수백 건 불필요, 실시간 단건 처리가 본질)

## 3. 목적과 제약

### 목적 (우선순위 순)
1. **RAM·디스크 점유 절감**: 현재 커밋 ~1GB가 부담. 모델 파일 471MB도 부담
2. **회수 품질 유지 또는 향상**: 특히 **한국어** semantic retrieval. 현재 모델은 한국어 벤치에서 동급 크기 대비 열위 (한국어 평균 0.41 vs mE5-small 0.67)
3. 지연 예산 내 유지 (1.5s)

### 하드 제약
- **로컬 CPU ONNX 추론만** (API 임베딩 불가)
- **384차원 또는 Matryoshka로 384 truncation 가능** (DB 스키마 유지 희망; 불가피하면 재임베딩 단계에서 차원 변경도 검토 가능)
- Windows + Python 런타임에서 로드 가능할 것 (fastembed 내장 목록에 없으면 ONNX 직접 로드로 우회 가능하나, 유지보수 단순성을 위해 fastembed/표준 sentence-transformers 호환이 우선)
- 라이선스: 상업/개인 사용 자유 (MIT/Apache 권장)

## 5. 의뢰 내용

1. **후보 목록 보강**: 위 표에서 누락된 2025~2026년 소형(<150M params, 우선 active params 기준) 멀티링구얼 임베딩 모델이 있는지. 특히 **한국어 성능이 검증된** 모델 환영.
2. **트레이드오프 판정**: 목적 1(RAM 절감)~3(지연) 제약에서 최적 후보 2~3개와 근거.
3. **한국어 검증 방법**: 각 후보의 한국어 semantic retrieval 품질을 벤치마크 전에 빠르게 가릴 수 있는 현실적인 방법 (기존 골드 50개 쿼리 재사용 외 권장 기법).
4. **전환 리스크**: 384차원 유지 시에도 벡터 공간 불일치로 인한 혼합 상태 위험, int8 양자화(vec_type) 재적용 시 품질 영향 등 교체 시 체크리스트.

### 판정 기준
- RAM: 모델 프로세스 커밋 총액 500MB 이하 (이하일수록 좋음)
- 품질: 한국어 회수 품질이 현재보다 명확히 향상 (골드 회귀 + MMTEB/한국어 벤치 근거)
- 지연: 쿼리 임베딩 p95 < 1s (CPU)
- 운영: fastembed 또는 표준 라이브러리에서 로드 가능하면 가산점

## 6. 기타 맥락

- 임베딩 모델 교체는 데몬 단일 지점 교체로 에이전트 측 변경은 불필요
- 기존 기억 전량 재임베딩은 백그라운드 배치로 수행 가능 (수천 행, 수 분~수십 분 예상)
- vec 레인을 아예 끄는 대안(FTS-only)도 검토했으나 회수 품질 하락이 커서 보류 중 — 모델 경량화가 더 나은 해법으로 판단
- 무료/키리스 환경이므로 유료 API 기반 제안은 제외

---

**응답 요청 형식**: 후보별 판정(채택/검토/기각) + 근거, 최종 추천 Top 2~3, 그리고 5번 항목 각각에 대한 답변.
