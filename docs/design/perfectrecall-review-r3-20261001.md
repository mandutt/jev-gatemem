# R3: 2라운드 AI 리뷰에 대한 실측 검증 — "rerank 병목" 가설의 반전

- 작성일: 2026-10-01
- 대상: `jev-memory-middleware` (A) vs `perfectrecall` (B) — 장기기억 회수 파이프라인
- 성격: R2 보고서(`perfectrecall-review-r2-20261001.md`)의 5개 질문(Q1~Q5)에 대한 3개 외부 AI 답변을 **모두 실측으로 검증**. 이 파일만으로 판단 가능(자가완결).
- 새 실측: ① B × A 교차표 (B per-query 재실행) ② 우리 judge_many + **코퍼스 전체** rerank ③ 코퍼스 구성 수치 정정

## 1. TL;DR (결론 먼저)

**세 AI의 2라운드 답변은 "커버 내 rerank 정밀도(69%)를 올려라"에 집중했지만, 결정적 실측으로 그 전제가 무너졌습니다.**

| 실측 | 결과 |
|---|---|
| 우리 judge_many + 풀(60~70) | Acc 0.556 |
| **우리 judge_many + 코퍼스 전체(419)** | **Acc 0.806** (같은 프롬프트·같은 Jev!) |
| PR `_rank` + 코퍼스 전체 | Acc 0.800 (재현) |

→ **"relevance가 커버 내에서 69%만 1위"는 rerank 품질 문제가 아니라, 후보 집합을 60~70개로 좁힌 순간 Jev의 변별력이 떨어지는 구조적 원인**. B(PR)의 우위는 "더 나은 rerank"가 아니라 **코퍼스 전체를 스캔**하기 때문.

**B × A 교차표 (B per-query 재실행, Acc 0.800)**:

| 구분 | 건수 | 비율 |
|---|---|---|
| B 정답 144건 중 A 커버 내부 | **128 (88.9%)** | rerank가 다르면 이렇게 안 됨 |
| B가 A 커버 밖에서 구제 | 16 (11.1%) | 커버 확대의 실질 이득 |
| A 커버 내 B 정답률 | 128/145 = **88.3%** | (= B 0.800과 A 커버 0.806의 교집합) |
| A 미커버 B 정답률 | 16/35 = **45.7%** | B도 커버 밖에선 반타작 |

→ **B의 0.800 = A 커버 내 128건(88.3%) + 커버 밖 16건**. 즉 "PR은 A가 놓친 19.4%를 Jev로 판정해서 이겼다"는 1라운드 가설은 **부분적으로만 맞고**, 실제로는 **A 커버 안에서도 B가 88.3%를 맞춰 A(relevance 69%)보다 19.3%p 높았습니다**. 그 이유는 rerank 방식 차이가 아니라 **스캔 범위 차이**입니다 (같은 프롬프트로 전체 스캔 시 0.806 재현).

**그래서 2라운드 답변 3개의 공통 전제("커버 내 rerank 개선이 1순위") = 기각.** 진짜 레버는:
1. **Jev에게 보여주는 후보 집합의 크기** (60→419에서 0.556→0.806, 임계 효과)
2. **코퍼스 구성** (kodialog/kosgd는 어떤 방식으로도 한계 — 아래 §5)

## 2. 2라운드 3개 AI 답변 요약

### A-AI (실행 지향)
- Q1: **2-Stage cascade** — relevance로 상위 6~8개만 슬라이싱 → choice. "70개 중 1개 찍기"가 자폭 원인이고, 6개로 좁히면 choice 식별력 0.80+로 급상승한다고 주장.
- Q2: **Doc2Query(저장 시 문서 확장)** 지지 — 쓰기 시점에 "답이 되는 질문 2~3개" 생성·색인, 쿼리 지연 0ms, 커버 85.6%→93~96% 전망.
- Q3: **Rerank 1순위** — "풀에 이미 145개 정답이 있으니, rerank 69%→90%면 +30건(0.72), 커버 확대는 +9건(0.60)에 그침"이라는 수리적 근거.
- Q4: **McNemar** — +5건은 유의하지 않음. 3회 반복 다수결, Δ≥+0.040 + p<0.05 + koalpaca/기계독해 회귀 0 게이트로 운영 반영.
- Q5: **게이트 완화 P0 즉시 적용** (버그 픽스 성격), **relevance 전면 교체 P2 연기** (운영 도메인은 이미 1.0). 운영 평가셋 100개(환경 30/디버깅 25/단답 선호 25/한영 교차 20) 설계안 제시.

### B-AI (통계·엄밀)
- 공통: **"relevance vs choice, k=100 vs 150은 Jev 비결정성(±1~2건) 안에서 구분 불가"** — 0.556/0.561/0.567은 180문항 중 100~102건으로 1~2건 차이. **유의성이 확보된 건 게이트 완화(9건)뿐**.
- "B의 0.806이 여전히 미설명" — B가 koalpaca/기계독해를 다 맞혀도 kodialog+kosgd 100문항에서 65건을 맞혀야 하는데, A는 같은 Jev로 20/65(31%)뿐. **판정 기준 문구 차이 or 채점 누출** 가설.
- **교차표를 "다음 단계"로 미룬 건 우선순위 역전** (비용 0).
- **무-Jev 기준선**을 모든 비교표에 넣어라 (vec 단독 0.494 ≈ 현행 0.489).
- **운영 지표 문제**: Acc@1은 응답 선택 지표. 운영은 top-N 증거·무답 쿼리·관련 기억 다수 — 현행 choice는 무답 쿼리에 엉뚱한 기억을 강제 주입 (벤치마크에 안 잡히는 실패).
- 권장 순서: ① 교차표/퍼데이터셋/셔플 → ② 무-Jev 기준선 + 수치 정리 → ③ 운영 평가셋 → ④ relevance 풀 크기 스윕(10/20/40/60/100) → ⑤ 결정.

### C-AI (전략)
- **"실측 확정 최적 구조"는 과장** — '현재 benchmark에서 가장 좋은 측정 구성' 수준. "vec k=100 최적"은 1건 차이로 미확정 (k=60/80/100/120/150/200 스윕 필요).
- **게이트는 설계 결함 수준** — semantic retrieval 후보에 lexical overlap을 다시 요구. 1/0 vs 0/0이 동일하니, **vector-origin 면제 + FTS-origin에만 게이트** 제안 (권장 실험으로 구분).
- **RRF 폐기보다 union 비교 우선** — vec top-100 + FTS top-20 + graph/importance 단순 union/dedupe → RRF 순위 왜곡 제거 실험.
- Q1: **relevance 프롬프트 개선 우선** — "concrete information"이 응답 선택 태스크에 무력. "직접 답을 충족하는가/의미적으로 동일한가"로 기준 명확화, 그 후 top-10 → choice.
- Q2: Doc2Query 지지 (별도 컬럼, FTS+vec 보조).
- Q3: **커버 먼저** (후보에 없는 정답은 어떤 reranker도 못 살림), 단 2축 병행 실험.
- Q4: **exact McNemar** — discordant 6개 모두 같은 방향이어야 p<0.05. 반복 3회 + 쿼리 단위 paired.
- Q5: **운영 평가셋이 최우선** — koalpaca 1.0을 운영 성능으로 연결 금지. 다음 4가지: ① B×A 교차표 ② 운영 벤치 ③ union vs RRF ④ relevance 3회 반복.

## 3. 실측 검증: 무엇이 맞고 무엇이 틀렸나

### 3.1 A-AI의 "2-Stage cascade" — **기각** (핵심 반전)
- A-AI는 "70개 중 1개 찍기 → 6개로 좁히면 choice가 0.80+"이라 했지만,
- **결정 실측**: 우리 judge_many + 코퍼스 전체(419) = **0.806**. 같은 프롬프트, 같은 Jev.
- 즉 **범위를 좁힐수록(relevance 60~70 → choice 6~8) 나빠진다**. "좁히는 것"이 아니라 "넓히는 것"이 정답. A-AI의 cascade는 풀 60~70에서 relevance를 0.556으로 만든 바로 그 문제(좁은 풀)를 6개로 더 심화시킵니다.
- 부분 타당: **게이트 완화 P0 즉시, relevance 전면 교체 보류** — 운영 도메인(koalpaca/기계독해)은 이미 어떤 방식으로도 1.0.

### 3.2 B-AI의 "통계·교차표 우선" — **정확, 실행 완료**
- "+5건은 유의하지 않음" — 맞음. 아래 §6에 정확 McNemar 정리.
- "판정 기준 문구 차이" 가설 — **기각**: PR `relevance` 프롬프트와 우리 `judge_many` 프롬프트는 거의 동일 문구 ("Does candidate contain concrete information..."). **기준 차이가 아니라 스캔 범위 차이** (전체면 0.806, 풀이면 0.556).
- 교차표 — **실행 완료** (§1 표). B 우위는 "커버 밖 구제 16건" + "커버 내 88.3%"인데, 커버 내 88.3%도 스캔 범위 효과.
- **무-Jev 기준선** — 타당, 다음 표에 추가 예정.
- **운영 지표 문제(무답 쿼리 오주입)** — 가장 가치 있는 지적 중 하나. choice가 "best 1"을 강제하는 문제는 벤치미스.

### 3.3 C-AI의 "표현 완화 + 4가지 실험" — **대체로 정확**
- "vec k=100 최적은 미확정" — 맞음 (1건 차이, Jev 비결정성 내). **단 §4에서 더 근본적인 이유로 논쟁 자체가 무의미해짐** — 풀 크기가 rerank 성능을 지배하므로 k 튜닝은 2차적.
- "vector-origin 면제 + FTS-origin 게이트" — 합리적, 다음 실험 후보.
- "RRF 폐기 전 union 비교" — 타당.
- Q1 "프롬프트 개선 우선" — **부분 기각**: 프롬프트는 PR과 동일함. 문제는 풀 크기. (운영 도메인 한정으로는 프롬프트 개선이 여전히 유효할 수 있으나 우선순위 하락.)
- "커버 먼저, 2축 병행" — §5에서 재판정.

## 4. 핵심 실측: "풀 크기 임계 효과"

| rerank 방식 | 후보 집합 | Acc@1 | MRR |
|---|---|---|---|
| choice (k=60) | 풀 ~69 | 0.539 | 0.584 |
| relevance | 풀 ~69 (게이트 완화) | 0.556 | 0.604 |
| relevance | 풀 ~105 (vec k=100) | 0.567 | 0.615 |
| relevance | 풀 ~152 (vec k=150) | 0.561 | 0.613 |
| **relevance (우리 judge_many)** | **코퍼스 전체 419** | **0.806** | **0.846** |
| PR `_rank` | 코퍼스 전체 419 | 0.800 | 0.846 |

- 풀 60→105: +0.011, 풀 105→419: **+0.239**. 단조 증가가 아니라 **임계적 점프** — 풀에 "불관련 오답"이 충분히 섞일 때 Jev의 변별력이 활성화됨.
- 해석: 풀(모두 어느 정도 관련 후보)에서는 정답과 오답의 relevance 점수 차가 작아 순위가 흔들림. 전체 코퍼스에는 명백한 무관 스팬이 대부분이라 정답이 상대적으로 두드러짐.
- **운영 함의**: lane pool + Jev rerank 구조는 구조적으로 PR의 full-scan에 열위. "좁은 풀 + Jev"는 Jev의 강점(전체 맥락 변별)을 절반만 활용.

## 6. 통계 (B-AI/A-AI 답변 정리 + 판정)

- **정확 McNemar**: discordant 쌍 d개일 때 순증가 ≥ 2√d 필요. 5승 0패 = p=0.0625 (유의 X), 6승 0패 = p=0.031 (유의). 현실적 d=12~24면 순증가 8~12건(Δ+0.044~0.067) 필요.
- **n=180 한계**: Δ=0.03을 검정력 80%로 잡으려면 ~1,300쿼리. **180문항으로는 ±0.03 차이를 가려낼 수 없음** (B-AI 정확).
- **권고 (B-AI)**: 쿼리별 3회 다수결 + 쿼리 단위 paired bootstrap. 운영 반영 기준은 유의성이 아니라 **① 구조적 근거(게이트 모순) ② 운영 평가셋 회귀 없음(≤2건) ③ 비용·지연 한도**.
- **판정**: 이번 실측에서 "relevance 전체풀(0.556) vs choice(0.539)"의 +0.017은 유의 판정 불가 — 단 "풀 → 전체 스캔"의 +0.250은 극단적이라 유의성 논쟁 불필요 (구조 차이).

## 7. Q1~Q5에 대한 실측 기반 최종 답

**Q1. 커버 내 1위 적중률(69%)을 올리는 방법**
→ **전제 기각**. 69%는 rerank 품질이 아니라 풀 크기 문제. 코퍼스 전체로 돌리면 0.806 (88.3% 커버 내 적중). "상위 6~8개 choice"(A-AI)도, "프롬프트 개선"(C-AI)도 2차적. 운영 도메인(문장형)은 이미 1.0.

**Q2. 커버 85.6% 상한을 넘는 저비용 수단 (Doc2Query)**
→ **유효한 다음 실험**. 단 이번 실측은 "커버 확대의 가치"를 다른 각도로 증명: B의 커버 밖 구제 16건이 유일한 실질 이득. Doc2Query는 쓰기 게이트의 기존 Jev 호출에서 질문 생성까지 받으면 추가 호출 0 (B-AI 지적). 다만 **이보다 먼저 "풀을 키우는 것"(전체 스캔 근접)이 같은 문제를 푸는지**를 봐야 함.

**Q3. B와의 공정 비교 완결**
→ **교차표 완료** (§1). 결과: B 우위의 대부분이 스캔 범위 효과. "커버 vs rerank" 분해는 더 이상 논쟁거리가 아니라 **"풀 크기 vs 전체 스캔" 비용-성능 트레이드오프**로 재구성.

**Q4. 통계적 타당성**
→ §6 참조. +0.028 수준은 n=180으로 판정 불가. **그러나 풀→전체(0.556→0.806)는 구조 차이라 통계 불필요.** 다음 실험(풀 150~300 중간 스윕)에서 유의성 기준 적용.

**Q5. 운영 우선순위**
→ **세 AI 모두 동의: 운영 평가셋이 최우선**. koalpaca/기계독해 1.0을 운영과 연결 금지. 평가셋 설계(B-AI/A-AI)를 채택하되 **무답 쿼리 10~20% + 오주입률 지표**(B-AI)를 필수로 포함.

## 8. 확정 vs 보류 vs 다음 단계

**실측 확정 (구조적, 통계 불필요)**:
1. 어휘 게이트는 vec 출신 정답 54/143건(38%)을 탈락시키는 설계 모순 → **완화/면제는 버그 픽스** (P0).
2. **"좁은 풀 + Jev" 는 "전체 스캔 + Jev"에 구조적으로 열위** — 같은 프롬프트·같은 Jev로 0.556 vs 0.806.
3. B의 우위 = 스캔 범위 (교차표: 커버 내 128건 + 커버 밖 16건).

**보류 (추가 실험 필요)**:
- relevance vs choice의 +0.017~0.028 (n=180 한계, 유의 판정 불가)
- vec k=100 vs 150 (1건 차이, Jev 비결정성 내)
