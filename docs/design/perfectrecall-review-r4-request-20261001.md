- **목적**: 3개 AI 리뷰어에게 현 상태(합성 벤치 종료, 메커니즘 검증 완료)를 공유하고, 다음 레버 결정에 대한 독립 검토를 요청
- **요청**: 이 문서만으로 상황을 파악할 수 있도록 작성. 아래 질문에 답변 요망.

## 1. 배경

JEV(Judge-Evaluate-Verify) + 경량 SQLite 방식의 메모리 시스템을 구축 중. 임베딩 모델은 `bench/bekko-a8m`(384차원, 로컬 fastembed)이고, JEV는 TypeSafe(SystemOne) API를 통해 호출되는 초저비용 LLM 판정기다.

- 180개 합성 쿼리(koalpaca/kosgd/kodialog 등, 사실형 80 + 대화 단답형 100)의 벤치마크가 완료됨.
- PerfectRecall(전체 코퍼스 brute-force 스캔 방식)과의 비교에서 **내 파이프라인 Acc@1 0.556 vs PerfectRecall 0.806**의 격차가 확인됨.
- R1~R3 리뷰에서 "합성 벤치마크는 졸업하고 운영 평가셋으로" 권고받아 합의됨.
- **본 문서(R4)는 그 전 단계인 "격차의 메커니즘 원인 규명" 결과와, 이후 레버 결정을 위한 검토 요청이다.**

## 2. 현행 파이프라인 구조 (J1)

1. **후보 생성 (lane pool)**: FTS 60 + vec 60 + importance 8 + graph 10 → RRF(k=30) merge → **상위 40개** 선택
2. **JEV rerank**: 상위 40개에 대해 JEV "choice" 1회 호출 → 1위 후보를 최상단으로 lift
3. **출력**: `## Mnemosyne Context` 블록 (top-5)

핵심: **JEV는 후보 40개만 본다. 40위 밖의 정답은 어떤 reranker로도 구제 불가.**

## 3. 실측된 사실 (모두 JEV 호출 0회 또는 최소로 확인)

### 3.1 메커니즘 검증 (이번 R4에서 새로 실측)

| 실험 | 결과 | 해석 |
|---|---|---|
| H1: 후보 순서 반전 | 점수 변화 매우 작음 (mean 0.010, max 0.040) | 순서 의존성 없음 |
| H2: 무관 후보 45개 추가 | 점수 변화 없음 (mean -0.001) | 앵커링 효과 없음 |
| **스캔 범위 419 vs 55 직접 비교** (같은 reranker, 같은 30쿼리) | **419: 0.767 / 55: 0.600** | **스캔 범위 효과 실존** — "전체를 보면 정답이 두드러진다" |

→ **B-AI의 반박("스캔 범위 효과는 앵커링")은 기각. "스캔 범위 자체가 정답 우위를 강화"가 실측됨.**

### 3.2 원인 분해 (PR 144건 맞춤 기준, 내 pool 55 재현)

| 범주 | 건수 | 비율 |
|---|---|---|
| A: pool에 정답 + PR reranker로도 맞출 수 있었던 | 128 | 71.1% |
| C: pool에 정답 없음 (recall 한계, reranker 무관) | 16 | 8.9% |
| D: PR 오답 + pool엔 정답 (reranker 개선 여지) | 17 | 9.4% |
| E: 양쪽 다 못 잡음 (구조적 한계) | 19 | 10.6% |

→ **격차의 60%는 "후보 생성 재현율(recall)" 차이** (C+E=35건). reranker 개선(D=17건)만으로는 부족.

### 3.3 후보 생성(recall) 개선은 토큰 0%로 가능한가? — 실측: 불가

| 개선 시도 | top-40 recall | 비고 |
|---|---|---|
| 현재 (RRF k60, POOL_BUDGET 40) | **141/180 (0.783)** | baseline |
| vec k=100으로 확대 | 141/180 (0.783) | 새로 잡힌 정답 9건 전부 top-40 **밖** (70~120위) |
| RRF → vec 단독 | 141/180 (0.783) | 동일 |
| RRF → union (vec60+fts20+graph10+imp10) | **140/180 (0.778)** | 오히려 -1건 |
| `_filter_and_rank` 가중치 8종 스윕 | 141/180 (0.783) | 전부 동일 |

→ **top-40 recall은 후보 생성·정렬·union으로는 0.783이 한계. 13건의 정답(vec 41~100위)은 임베딩 유사도가 낮아 어떤 merge로도 40위 안에 못 들어옴.**

### 3.4 POOL_BUDGET 확대는 토큰을 늘린다

| POOL_BUDGET | top-N recall | JEV 토큰 증가 |
|---|---|---|
| 40 (현행) | 0.783 | 기준 |
| 50 | 0.789 | +25% |
| 60 | **0.806** | +50% |
| 100 | **0.856** | +150% |

→ **top-40 recall을 올리는 유일한 레버는 POOL_BUDGET 확대이며, 이는 JEV 토큰 증가와 직결.**

### 3.5 재현율(recall) 자체의 개선 (JEV 토큰 0%)

vec k=100으로 후보 풀을 100개로 넓히면 **풀 전체 recall은 145→154 (0.806→0.856)로 오른다.** 그러나 위 3.3에서 확인했듯 **top-40 recall은 0.783 고정** — 즉 JEV가 보는 40개 안에는 변화가 없다.

## 4. 질문 (검토 요청)

### Q1. 최종 결론의 타당성
"격차의 60%는 후보 생성 재현율 차이, reranker 개선 여지는 9.4%(D=17건)뿐"이라는 분해가 타당한가? 간과된 요소가 있는가?

### Q2. POOL_BUDGET 확대 vs 운영 평가셋
- POOL_BUDGET 40→60 (+50% 토큰)으로 top-N recall 0.783→0.806
- POOL_BUDGET 40→100 (+150% 토큰)으로 0.783→0.856
- **다만 이는 "합성 벤치(대화 단답 55%)" 기준.** 운영 환경(Hermes 코드/설정/선호 메모리)에서는 이 단답 대화 쿼리가 거의 없다.

이 상황에서 (a) POOL_BUDGET을 먼저 확대할 가치가 있는가, (b) 아니면 운영 평가셋(60문항)에서 재측정 후 결정하는 것이 옳은가? 토큰 예산 관점의 권고?

### Q3. "스캔 범위 효과"의 활용
전체 419를 스캔하면 정답 우위가 강화된다(0.767 vs 0.600)는 실측이 나왔다. 이를 **토큰 증가 없이** 활용할 방법이 있는가?
- 예: 후보를 상위 40개만 JEV에 주는 대신, **후보 40개 + 무관 후보 K개(명백한 오답)** 를 함께 주어 판정 척도를 교정하는 앵커링 — 이번 실측(H2)에서는 앵커 효과가 없었지만, "명백한 무관 후보"와 "그럴듯한 무관 후보"의 차이가 있을 수 있는가?
- 예: JEV choice 대신 relevance 스코어링 + threshold 활용

### Q4. 합성 벤치 졸업의 타당성
"남은 미스 35건은 100% kodialog/kosgd(대화 단답)이며, Hermes 운영에는 이 태스크가 없다"는 전제로 합성 벤치를 졸업하는 것이 타당한가? 혹시 운영에도 이와 유사한 "짧은 응답 메모리" 태스크가 있을 수 있는가?

### Q5. 운영 평가셋 설계 (60문항) 검토
이전 리뷰에서 제안된 운영 골든셋 구성:
- A. 환경/설정 팩트 15, B. 에피소딕 인과/디버깅 15, C. 사용자 단답 지침/선호 15, D. 한-영 교차 코드/CLI 15
- 현행(A) Acc@1 ≥ 0.90 (54/60)이면 종결

이 구성에 대한 의견, 그리고 "무엇을 측정해야" 이번 합성 벤치의 한계를 보완하는지에 대한 제안?
