## 2. 시스템 개요 (R1과 동일, 자가완결용)

| | 구현 A (본인, 운영 중) | 구현 B (PerfectRecall) |
|---|---|---|
| 회수 방식 | **lane pool 하이브리드**: FTS + 벡터 + importance + graph 4개 lane → RRF → 어휘 게이트 → **Jev 1회 choice** | **full-corpus 스트리밍 스캔**: SQLite 전체 행 순회 → **모든 후보 Jev relevance 배치** → 임계값 0.5 |
| 임베딩 | **bekko-embedding-v1-a8m** (384차, int8, ONNX CPU) | 없음 |
| Jev 사용 | 쿼리당 **1회** | 쿼리당 **코퍼스 크기 비례** (180쿼리×10 = 1,800회) |
| 저장 게이트 | 있음 (Jev store/type) | 없음 (무조건 저장) |

**실행 환경**: Windows 11, CPU only, RAM 15.6GB (민감), Python 3.14 venv, sqlite-vec int8. Jev = TypeSafe SystemOne (`api.typesafe.ai/v1/systemone`, `jev-latest`), 타임아웃 15s + 재시도 1회.

**평가 프로토콜 (격리·동일 조건)**: 스크래치 전용 DB, 코퍼스 **419 스팬** (kodialogbench 300 후보 / koalpaca 40 / kosgd 40 / 기계독해 40), 쿼리 **180개**. 같은 DB·쿼리·seed(42)·Jev 엔드포인트·키. 실 운영 DB/Hermes/config 무접촉. B용 DB는 a8m 419건 백필 후 측정.

**지표**: Acc@1, MRR, 지연/쿼리, Jev 호출 수, 프로세스 메모리, ±토큰.

## 3. 누적 실측 결과 (R1 → R2 → R3)

### 3.1 메인 비교 (180쿼리, 코퍼스 419, R1)

| 지표 | A: lane pool + 게이트 + choice | A': 게이트 완화 + choice | B: full-scan |
|---|---|---|---|
| **Acc@1** | 0.489 | **0.539** | **0.806** |
| **MRR** | 0.556 | 0.584 | **0.849** |
| 지연/쿼리 | 0.23s | 0.28s | 0.38s |
| Jev 호출(180) | 179 | 180 | **1,800** |
| 프로세스 메모리 | 615MB | 615MB | **12MB** |

### 3.2 레이어 분해 (동일 419 코퍼스)

| 구성 | Acc@1 | 비고 |
|---|---|---|
| 임베딩 단독 (쿼리-후보 코사인) | **0.672** | "모델이 나쁘다"가 아님을 증명 |
| vec 단독 → RRF (무-Jev) | 0.494 → 0.467 | RRF가 vec을 크게 망가뜨리지 않음 (1라운드 오해 교정) |
| RRF + 게이트 (원래) | 0.461 | |
| RRF + 게이트 완화 + Jev choice | **0.539** | 현행 운영 |
| RRF + 게이트 완화 + Jev relevance (풀 60~70) | 0.556 | choice보다 +0.017 |
| **같은 relevance + 코퍼스 전체(419)** | **0.806** | ★후보 집합 크기가 결정적 레버 |
| PR `_rank` + 코퍼스 전체 | 0.800 | 재현 |

**핵심 통찰 (R3 실측)**: "relevance가 커버 내 69%만 1위"는 rerank 품질 문제가 아니라 **후보를 60~70개로 좁힌 순간 Jev 변별력이 떨어지는 구조적 현상**. 같은 프롬프트로 후보만 419개로 늘리면 0.806.

### 3.3 B × A 교차표 (B per-query 재실행, Acc 0.800)

| 구분 | 건수 | 비율 |
|---|---|---|
| B 정답 144건 중 A 커버 내부 | 128 | 88.9% — rerank가 다르면 이렇게 안 됨 |
| B가 A 커버 밖에서 구제 | 16 | 11.1% — 커버 확대의 실질 이득 |
| A 커버 내 B 정답률 | 128/145 | 88.3% |
| A 미커버 B 정답률 | 16/35 | 45.7% (B도 커버 밖에선 반타작) |

→ B의 우위 = "커버 밖 16건 구제" + "커버 내 88.3%". 둘 다 rerank 방식 차이가 아니라 **스캔 범위(후보 수)** 효과.

### 3.4 데이터셋별 분해 (R2/R3)

| 데이터셋 | 커버 (게이트 완화 후) | 특성 |
|---|---|---|
| koalpaca (40) | 40/40 = **100%** | 사실형 — 어떤 rerank도 1.0 |
| 기계독해 (40) | 40/40 = **100%** | 사실형 — 어떤 rerank도 1.0 |
| kodialog (60) | 39/60 = 65% | **응답-선택** (무의미한 짧은 응답) |
| kosgd (40) | 26/40 = 65% | **응답-선택** (다음 발화) |

→ **미스 35건은 전부 응답-선택 태스크**. 사실형 도메인은 이미 100% 커버.

## 4. 이번 라운드 새 실측 (R3 → 최종 결정)

### 4.1 union vs RRF — **180쿼리 전체 실측으로 기각** (1라운드 C-AI 제안)

- **제안**: "RRF 폐기 전, vec top-60 + FTS top-20 + graph top-10 + importance top-10을 **단순 union/dedupe**로 — RRF 순위 왜곡 제거, 토큰 절약".
- **60쿼리 서브셋 파일럿** (kodialog 20/koalpaca 20/기계독해 20, kosgd 제외): union 0.717 vs RRF 0.717 **동률**, "union 토큰 절반(1.92M vs 3.89M)" — 이 수치로 union 승리로 보였음.
- **그러나 180쿼리 전체 실측** (kosgd 40 포함, 같은 Jev relevance, 같은 lane 예산):

| 구성 | 후보 수 (평균) | Acc@1 | 커버 | 입력토큰 (180쿼리) |
|---|---|---|---|---|
| RRF relaxed | 68.7 | **0.5556** | 145 (80.6%) | (동급) |
| union | 66.3 | **0.5556** | 145 (80.6%) | 4.43M |

→ **완전 동률**. union은 RRF 대비 성능 이점 0, 토큰 절약도 미미(후보 수가 거의 같음). "union 0.717·토큰 절반"은 **kosgd 제외 lucky subset 착시**였음.
- **결론: RRF 유지** (union의 후보 순위 왜곡 제거 효과가 없고, RRF는 coverage를 소폭 늘리는 순기능 보유).

### 4.2 Doc2Query — **파일럿 실측으로 기각** (1·2라운드 A/B/C 공동 제안)

- **제안**: 저장 시 "이 기억이 답이 되는 질문" 2~3개 생성·색인 (쿼리 지연 0, 커버 85.6% → 93~96% 전망).
- **파일럿 실측**: 커버 미스 23건(전수 분석) → **전부 kodialog/kosgd 응답-선택**. "오, 음, 됐어요." 같은 응답은 **어떤 질문의 답도 아니므로 질문 생성 자체가 불가능**.
- 사실형 도메인(koalpaca/기계독해)은 이미 100% 커버 → Doc2Query가 구제할 미스가 없음.
- 10개 샘플 질문 생성(로컬 deepcombo) → 커버 변화 **0** (10/10 → 10/10).
- **결론: 이 벤치마크 도메인에서는 Doc2Query 실익 0**. 단, 운영 도메인(짧은 단답 선호 등)에서는 유효할 수 있으나 벤치로 검증 불가 — 운영 평가셋(§6 Q4)에서 판정할 항목으로 이관.

### 4.3 lane budget 60 유지 (1라운드 A "k=100 최적" 제안)

- k=100: Acc 0.567 (정점, +0.028), 커버 85.6% (+5%p) ↔ 토큰 +67% (3.71M → 6.19M)
- **사용자 결정: 기각** — "토큰 증가량 대비 상승폭이 크지 않다". `LANE_VEC_BUDGET=60` 유지.

### 4.4 게이트 완화 — 운영 라이브 반영 완료

- `core/j1_engine.py` 기본값 (2,0.30) → **(1, 0.0)**. 커밋 `c3aee3a`, 데몬 재기동, 라이브 prefetch 검증 완료.
- 1/0과 0/0 실측 동일 → 사실상 **vector-origin 게이트 면제 + FTS-origin만 lexical** (C-AI 제안과 동일 효과).

## 5. 남은 미해결 문제 (3라운드에 물어볼 것)

### 5.1 "커버 80.6%의 벽"을 넘는 저비용 방법?

- 당연한 수확(커버 내 rerank 개선)은 **유의한 레버가 아님** — 커버 내에서 Jev가 69%만 1위에 올리는 이유는 rerank 품질이 아니라 후보 집합 크기(60~70)임을 실측으로 확인. 풀을 키우면(419) 0.806이지만 **Jev 토큰이 코퍼스 비례 폭발** (180쿼리 4.39억 토큰, 세션의 91%).
- k=100 상향: +0.028에 +67% 토큰 → 기각.
- union: 의미 없음 → 기각.
- **남은 후보**: (a) **2-stage** — 1차 풀 60으로 충분하면 그대로, Jev 신뢰도 낮거나 빈 결과면 확장 스캔? (b) **FTS/vec k를 쿼리 유형별 차등**(사실형 vs 응답-선택)? (c) **importance 0.85 이상 메모리에 대한 상시 포함**(이미 존재)? (d) relevance 프롬프트 개선(§5.3)? 어느 것이 가장 비용 대비 우위일까?

### 5.2 응답-선택 태스크(kodialog/kosgd)의 커버 65% 한계

- 35건 미스가 전부 응답-선택. 사실형은 100%. **이 태스크 유형에서 커버를 올릴 방법이 있는가?** (벡터/FTS로는 짧은 응답과 대화 맥락의 의미 매칭이 어려움)
- B도 미커버 35건 중 16건(45.7%)만 구제 — **B도 응답-선택에선 반타작**.

### 5.3 relevance 프롬프트 개선 (C-AI 제안, 미실험)

- "Does candidate contain concrete information useful to answer state.query?" → **"직접 답을 충족하는가 / 의미적으로 동일한 사건·정보인가 / 단순 주제 유사성이 아닌 실제 답변에 필요한 memory인가"** 로 명확화.
- 응답-선택 태스크에서 커버 내 rerank 정확도가 올라갈까? (저렴한 실험이지만 Jev 비결정성 ±1~2건 대비 유의한 차이가 나올까?)

### 5.4 운영 평가셋 (3개 AI 공동 권장, 미착수)

- 벤치(한국어 대화·다음 발화)와 운영(코딩 에이전트 장기기억) 도메인이 다름. A-AI 제안: 환경 30 / 디버깅 25 / 단답 선호 25 / 한영 교차 20. 이 구성이 적절한가?

### 5.5 통계 판정 기준

- n=180에서 Δ≥+0.028은 McNemar 미유의(±1~2건 = Jev 비결정성 범위). **운영 반영 게이트로 Δ≥+0.040 + p<0.05 + 사실형 회귀 0**이 합리적인가?

## 6. R3 리뷰 질문 (답변 요청)

1. **Q1 (최우선)**: 현재 확정 구조(RRF k=60 + 게이트 완화 + Jev choice, Acc 0.539)에서 **다음으로 실측할 가치가 가장 높은 단일 실험**은 무엇인가? (커버 80.6% 벽, 토큰 민감, Jev 비결정성 ±1~2건, 운영 도메인 상이 — 위 4가지 후보 중 또는 새 제안)
2. **Q2**: §5.2의 응답-선택 태스크 커버 65% 한계를 넘을 방법이 실제로 있는가? (이 태스크 유형이 벤치에만 있는 인공물인지, 운영에도 존재하는지 포함)
3. **Q3**: relevance 프롬프트 개선(§5.3) — 실측할 가치가 있는가? 있다면 어떤 기준 문구가 이 태스크에 가장 적합한가?
4. **Q4**: 운영 평가셋(§5.4) — 실용적인 구성(항목 수·도메인 분포·수집 방법)을 구체적으로 제안해 달라. 벤치 수치를 운영 성능으로 연결하는 게 금지인 이유는 무엇인가?
5. **Q5**: 지금까지의 판정 기준(§5.5) — 통계 게이트로 충분한가? Jev 비결정성이 큰 환경에서 n=180 벤치로 구조 결정을 내리는 것이 타당한가, 아니면 더 나은 평가 설계가 있는가?
