제공해주신 아키텍처 브리프를 면밀히 검토했습니다. 

결론부터 말씀드리면, **"중앙 집중형 Core-as-Writer(데몬 프로세스) 구조"는 주어진 환경 제약(Windows 11, 15.6GB RAM, Docker 미사용, fastembed 중복 로드 금지)에서 취할 수 있는 가장 현실적이고 올바른 방향**입니다. 

다만, 제안서에 기술된 일부 세부 설계(특히 **"단일 스레드 완전 직렬화"** 및 **트랜스포트 계층 선택**)는 실제 멀티 에이전트 동시 구동 시 치명적인 지연(Head-of-Line Blocking)을 유발할 위험이 있습니다.

문서 7장에 기술된 6가지 검토 질문을 중심으로 구조적 타당성, 위험 요소, 최적의 대안을 상세히 검토한 결과를 보고서 형태로 제시합니다.

### 1. 중앙 집중형 Core-as-Writer의 타당성 (Q1)

#### ✅ 판정: 전적으로 타당하며, 다른 대안 대비 압도적으로 유리합니다.
- **메모리(RAM) 제약 해결의 유일한 해법:** `BeamMemory`에 내장된 `fastembed`(ONNX Runtime 기반 임베딩 모델)는 프로세스당 수백 MB의 RAM을 상주 점유합니다. Hermes, pi, Codex, opencode가 각각 임베디드 형태로 이를 로드하면 모델 중복 로드만으로 1~2GB의 메모리가 낭비되며, 15.6GB 환경에서는 OS 페이징 압박을 유발합니다. 임베딩 모델을 단일 프로세스에만 상주시키는 것만으로도 이 구조의 가치는 충분합니다.
- **기각된 대안들의 한계 재확인:**
  - **다른 DB 엔진(PostgreSQL, Qdrant 등) 도입:** Docker를 배제하고 Windows 네이티브로 독립 서비스형 DB를 유지·관리하는 것은 배포 및 유지보수 비용이 과도하며, `mnemosyne` 라이브러리 내부(`BeamMemory`)를 전면 재작성해야 합니다.
  - **Append-only 로그 + 백그라운드 인덱서:** 쓰기는 빠르지만, 방금 쓴 대화 턴이 색인되기 전까지 다른 에이전트의 prefetch에서 누락되는 **읽기 일관성 지연(Eventual Consistency lag)** 문제가 발생합니다.
- **개념의 확장 (DB 프록시가 아닌 "메모리 런타임"):**
  `jev-mem-core`는 단순한 SQLite 쓰기 중계기가 아니라, **"fastembed 벡터화 + JEV API 리랭킹 + 쓰기 게이트 판정 + DB 트랜잭션"을 총괄하는 전용 추상화 데몬**으로 정의하는 것이 적합합니다.

### 2. 트랜스포트 계층 선택 (Q2)

#### 💡 권고: TCP 소켓(JSON-RPC)보다 "로컬 HTTP (REST / JSON)"를 강력히 권장합니다.

| 비교 항목 | Raw TCP (JSON-RPC) | 로컬 HTTP (FastAPI / aiohttp) |
|---|---|---|
| **Codex CLI 훅 연동** | 별도 TCP 클라이언트 래퍼 스크립트 작성 필요 | `curl` 또는 PowerShell `Invoke-RestMethod` 한 줄로 즉시 연동 가능 |
| **pi (TypeScript) 연동** | `net.Socket` 프레임 분할(LF/길이 프리픽스) 직접 구현 필요 | 표준 `fetch()` API로 5줄 이내 구현 가능 |
| **디버깅 / 관측성** | 패킷 덤프 또는 전용 CLI 필요 | 브라우저/Swagger/curl로 즉시 상태 확인 가능 (`/health`) |
| **오버헤드** | ~0.1ms | ~0.5ms (Loopback HTTP) |

- **오버헤드 분석:** JEV API 네트워크 지연이 **~275ms**인 시스템입니다. HTTP 핸드셰이크와 파싱 오버헤드(0.5ms 이하)는 전체 지연시간의 **0.2% 미만**에 불과하여 성능상 불이익이 전무합니다.
- **Codex CLI hook의 현실적 문제:** Codex CLI의 config hook(`Stop` 등)은 보통 짧은 쉘 커맨드를 실행합니다. TCP 소켓 기반 프로토콜을 사용하면 쉘에서 바로 쏠 수 없어 매번 파이썬 인터프리터를 새로 띄워 통신해야 하므로 프로세스 스폰 비용(100~200ms)이 오히려 더 큽니다. 반면 HTTP는 `curl`로 수 밀리초 만에 비동기로 던질 수 있습니다.
- **구현 권고:** Python `FastAPI` (또는 경량 `Starlette` + `uvicorn`)를 127.0.0.1의 고정 로컬 포트(예: `127.0.0.1:28414`)에 바인딩하십시오.

### 3. 동시성 모델: 단일 스레드 직렬화 vs 비동기 + 쓰기 락 (Q3)

#### ⚠️ 핵심 경고: "단일 스레드 순차 실행"은 심각한 병목(Head-of-Line Blocking)을 유발합니다.

제안서 5.2절의 *"core 내부는 단일 스레드로 모든 요청을 순차 실행"* 방식은 치명적인 결함이 있습니다:
1. `sync_turn` 요청이 들어오면 JEV API(Write Gate)를 호출해 판정하는 데 **최소 300~800ms**가 소요됩니다.
2. 이때 사용자가 다른 에이전트(pi)에서 엔터를 쳐서 `prefetch`가 발생하면, 앞선 `sync_turn`의 JEV API 응답이 올 때까지 **사용자 UI가 완전히 프리징**됩니다.

#### 🛠️ 해결책: "비동기 I/O (AsyncIO) + SQLite 쓰기 전용 세마포어"

```
[클라이언트 요청들 (HTTP)]
       │
       ▼
 ┌────────────────────────────────────────────────────────┐
 │ jev-mem-core (AsyncIO 이벤트 루프)                      │
 │                                                        │
 │  1. prefetch() ──> JEV API 비동기 호출 (병렬 처리 가능)  │
 │        │                                               │
 │        └──> DB 읽기 (WAL 모드, 병렬 읽기 허용)          │
 │                                                        │
 │  2. sync_turn() ─> JEV Gate 비동기 호출 (병렬 처리 가능)│
 │        │                                               │
 │        └──> [ asyncio.Lock (Write Lock) ] ──┐          │
 │                                             │          │
 └─────────────────────────────────────────────┼──────────┘
                                               ▼
                                      SQLite 쓰기 (<5ms)
```

- **외부 API(JEV API) 호출:** 비동기(`httpx.AsyncClient`)로 동시에 수십 개를 병렬 처리합니다.
- **SQLite 읽기 (prefetch lane 검색):** SQLite WAL 모드에서는 읽기와 쓰기가 서로를 블로킹하지 않습니다. 병렬 읽기가 안전하게 허용됩니다.
- **SQLite 쓰기 (remember):** JEV Gate 판정이 끝난 뒤, **실제 DB에 INSERT하는 짧은 순간(수 밀리초)에만 `asyncio.Lock`을 획득**하여 직렬화합니다.
- **결과:** 쓰기 충돌은 100% 원천 방지되면서, 외부 API 지연으로 인한 읽기 병목이 완벽히 해소됩니다.

### 4. Hermes 플러그인 전환 리스크 및 듀얼 모드 평가 (Q4)

#### ❌ 권고: "임베디드 모드로의 Fallback(듀얼 모드)"은 절대 구현하지 마십시오.

브리프에서 검토된 듀얼 모드(core 죽으면 로컬 DB 직접 접근)는 **위험한 안티패턴**입니다:
1. **분할 뇌(Split-Brain) 및 DB 잠금 충돌:** core가 일시 정지되었다가 깨어났거나, Hermes가 코어 다운으로 오판해 임베디드로 전환하는 순간 다시 "복수 Writer" 상태가 되어 SQLite `busy/locked` 충돌이 재발합니다.
2. **메모리 이중 점유:** fallback 코드가 Hermes에 남아있다면, Hermes 프로세스 venv 역시 `fastembed`, `torch/onnx` 의존성을 유지해야 하므로 메모리 절감 효과가 반감됩니다.
3. **복잡도 폭증:** 테스트해야 할 경우의 수가 2배로 증가합니다.

#### 🛡️ 안전한 전환 전략:
- **Soft Degradation (우아한 기능 저하):** core 응답 없음 시 기존 계약대로 prefetch는 `""`(빈 블록), sync_turn은 `DROP + 로컬 로그 기록`으로 처리합니다. (문서 5.5절의 방침 유지)
- **데몬 자동 기동 (Self-Healing Lazy Spawn):**
  Hermes 플러그인 초기화 시 `GET http://127.0.0.1:28414/health`를 확인하고, 응답이 없으면 Hermes 플러그인이 백그라운드로 `python -m jev_mem_core`를 직접 `DETACHED_PROCESS`로 띄우도록 보조 로직을 두는 것이 듀얼 모드보다 훨씬 안전합니다.

### 5. 놓치기 쉬운 고장 모드 및 엣지 케이스 (Q5)

Windows 11 네이티브 환경에서 반드시 사전에 방어해야 할 5가지 장애 시나리오입니다.

1. **Windows 파일 핸들 잠금 (Mandatory Locking) 잔류:**
   - Windows는 프로세스가 비정상 종료(SIGKILL, 강제 종료)될 때 SQLite `.db-wal`, `.db-shm` 파일의 잠금이 즉각 풀리지 않는 경우가 있습니다.
   - **대책:** Core 시작 시 SQLite 파일 접근 가능 여부를 체크하고, 잠겨 있다면 2초 간격 3회 재시도 후 명확한 에러 메시지를 출력해야 합니다. 프로세스 종료 시 `atexit` 및 `win32` 콘솔 컨트롤러 핸들러를 등록해 DB 커넥션을 명시적으로 `close()`하도록 보장하십시오.
2. **클라이언트 사이드 타임아웃의 부재:**
   - JEV API가 먹통이 되거나 Core가 무한 루프에 빠지면 에이전트(Hermes/pi) 턴 전체가 멈춥니다.
   - **대책:** 에이전트 어댑터의 HTTP 클라이언트는 **prefetch 타임아웃을 최대 1.5초~2.0초로 하드 제한**하고, 초과 시 즉시 TimeoutError를 캐치하여 빈 Context 블록을 반환해야 합니다. (사용자 경험 최우선)
3. **Fastembed의 ONNX 스레드 경합:**
   - 멀티 에이전트가 동시에 prefetch를 요청하여 Core 내에서 fastembed 임베딩 추론이 동시에 돌면 CPU 점유율이 100%로 치솟을 수 있습니다.
   - **대책:** fastembed 호출부에 `asyncio.Semaphore(1)` 또는 `(2)`를 걸어 CPU 바운드 추론 동시 실행 수를 제한하십시오.
4. **고스트 프로세스 및 포트 점유:**
   - 이전 Core 프로세스가 백그라운드 좀비로 남아 포트를 잡고 있으면 새 Core가 `EADDRINUSE`로 크래시됩니다.
   - **대책:** Core 기동 시 해당 포트를 이미 점유 중인 프로세스가 정상 동작하는 Core인지 `/health`로 확인하고, 응답이 없거나 비정상이면 PID를 추적해 정리하거나 경고를 띄워야 합니다.

### 6. 확장 한계 및 재설계 임계점 (Q6)

- **현재 구조의 실제 한계:**
  - 개인 작업 환경에서 에이전트가 10개로 늘어나도, **초당 사용자 발화 수는 인간의 타이핑 속도에 수렴(최대 1~3 QPS)**합니다. 
  - SQLite의 WAL 모드 단일 Writer 처리량은 초당 수백~수천 건의 트랜잭션입니다. 따라서 **SQLite 쓰기 용량 때문에 재설계할 일은 로컬 환경에서 사실상 없습니다.**
- **진짜 병목 지점:**
  1. **TypeSafe JEV API Rate Limit / 동시성 한도:** 여러 에이전트가 동시에 대화할 때 JEV API의 429(Too Many Requests)가 가장 먼저 발생할 것입니다. (Core 내부에 지수 백오프 재시도 및 요청 큐 필수)
  2. **SQLite WAL 파일 무한 비대화:** 장수 프로세스가 DB 커넥션을 계속 열어두면 WAL 체크포인트가 정상 수행되지 않아 `mnemosyne.db-wal` 파일이 수 GB로 커질 수 있습니다. (주기적으로 `PRAGMA wal_checkpoint(PASSIVE)` 실행 필요)
- **재설계가 필요한 시점:**
  - "단일 머신 로컬 환경"을 벗어나 **팀 단위 원격 공유 메모리**가 필요해질 때. 이때 비로소 독립 Vector DB(Milvus/Qdrant) 및 클라우드 RDBMS로의 전환이 요구됩니다.

### 7. 최종 검토 의견 요약 및 액션 아이템

| 영역 | 브리프 원안 | **검토 후 권고안** |
|---|---|---|
| **아키텍처** | Core-as-Writer 데몬 | **원안 채택 (강력 권장)** |
| **트랜스포트** | TCP localhost (JSON-RPC) | **로컬 HTTP (FastAPI / Starlette) 채택** (Codex CLI 및 TS 연동성 극대화) |
| **동시성 처리** | 단일 스레드 순차 직렬화 | **AsyncIO 비동기 (JEV 병렬 호출) + 쓰기 전용 Lock (<5ms)** |
| **장애 모드** | core 미실행 시 embedded 듀얼 모드? | **듀얼 모드 완전 배제 + Soft-fail (빈 블록 반환) 고수** |
| **프로세스 관리** | Windows 스케줄러 수동 등록 | **어댑터의 Lazy-spawn (부재 시 자동 기동) 보조 추가** |

제안하신 `Core-as-Writer` 아키텍처는 기술적 제약조건을 매우 잘 파악한 훌륭한 설계입니다. 위에서 제시한 **"HTTP 채택"**과 **"I/O 병렬화 + DB 쓰기 국소 락"** 두 가지만 반영하여 구현을 진행하시면, Hermes를 비롯한 모든 서브 에이전트가 충돌 없이 빠르고 견고하게 메모리를 공유할 수 있을 것입니다.
