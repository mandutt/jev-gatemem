# 비교 실측 보고서: lane-pool 하이브리드 vs PerfectRecall (Jev full-scan)

- **작성일**: 2026-10-01
- **목적**: 타 AI의 독립적 조언을 구하기 위한 **자가완결형 실측 보고서**. 이 문서만으로 판단 가능.
- **핵심 질문**: 임베딩 모델을 유지하면서 회수 정확도를 높이려면 어떻게 해야 하는가? (Jev 호출 수 증가는 일정 수준 허용)

---

## 1. 시스템 개요

로컬 AI 에이전트(Hermes)의 장기기억 시스템. 두 구현이 동일한 기억 스키마(SQLite, Mnemosyne 포크 계열)를 쓰지만 회수 아키텍처가 다르다.

| | 구현 A (본인, 운영 중) | 구현 B (PerfectRecall, github.com/arslanr-com/perfectrecall) |
|---|---|---|
| 회수 방식 | **lane pool 하이브리드**: FTS(어휘) + 벡터(임베딩) + importance + graph 4개 lane → RRF 병합 → 어휘 게이트 → **Jev 1회 choice rerank** | **full-corpus 스트리밍 스캔**: SQLite 전체 행을 순회 → **모든 후보를 Jev relevance 배치로 평가** → 임계값(0.5) 이상만 |
| 임베딩 모델 | **bekko-embedding-v1-a8m** (384차, int8 양자화, ONNX CPU) | **없음** (임베딩/벡터 인덱스 자체가 없음) |
| Jev 사용 | 쿼리당 **1회** (후보 풀에서 "best 1개" choice) | 쿼리당 **코퍼스 크기에 비례** (후보 전부에 noul relevance) |
| 저장 게이트 | 있음 (Jev가 store/type 판정) | 없음 (무조건 저장) |

**실행 환경 (공통)**: Windows 11, x86-64 CPU 전용(No GPU), RAM 15.6GB, Python 3.14 venv, sqlite-vec(0.1.9, int8). Jev = TypeSafe SystemOne (`api.typesafe.ai/v1/systemone`, `jev-latest`), 타임아웃 15s, 재시도 1회.

**운영 제약**: RAM 민감(현재 a8m 데몬 Private Commit 615MB — 이전 MiniLM 947MB 대비 -35%). 비용 민감. Docker 불가(네이티브 필수). 배포 시 다국어(한/영 외) 지원 필요.

## 2. 평가 프로토콜 (격리 · 동일 조건)

- **데이터**: 스크래치 전용 SQLite DB, 코퍼스 **419 스팬**
  - kodialogbench(한국어 대화 응답 5지선다) 60아이템 × 5후보 = 300
  - koalpaca(한국어 지시문→출력) 40아이템(풀 40)
  - kosgd(한국어 맥락→다음 발화) 40아이템(풀 40)
  - 기계독해(기술과학 문서 오프닝→문서) 40아이템(풀 40)
- **쿼리**: 180개 (위 아이템의 쿼리). 임베딩 단독 실측 시 쿼리·후보 모두 실측 임베딩.
- **동일 조건**: 같은 DB, 같은 쿼리, 같은 seed(42), 같은 Jev 엔드포인트·키. 실 운영 DB/Hermes/config 무접촉.
- **내부 검증 보정**: 구현 B(임베딩 없는 포크)가 만든 DB는 임베딩 0건 → 구현 A 측정 전에 a8m으로 419건 백필 후 재측정(안 하면 벡터 lane이 죽은 채 측정됨).
- **지표**: Acc@1, MRR(정답 후보의 역순위), 쿼리당 지연, Jev 호출 수, 프로세스 메모리.

## 4. 원인 분석 (실측 기반)

1. **B(PR)의 우위 = 전체 코퍼스를 Jev에 노출**: A는 lane pool이 정답을 놓치면(19.4%) 회생 불가. PR의 Acc 0.806 ≈ A의 lane pool 커버 80.6%와 **수치상 정확히 일치** — 즉 B는 "A가 놓친 19.4%까지 Jev로 판정"해서 이긴다.
2. **A의 랭킹 병목은 임베딩이 아니라 lane pool 순위 + choice 방식**:
   - 임베딩 단독(직접 유사도)은 0.672인데 lane pool(RRF)은 0.467 — **RRF 병합이 임베딩 단독보다 정답 순위를 떨어뜨림** (어휘/그래프 lane의 노이즈가 상위를 오염).
   - kodialog은 커버 39/60인데 rerank 후에도 Acc 0.100 → **정답이 pool에 있어도 Jev choice(70개 중 1개 선택)가 못 찾음**.
3. **A의 어휘 게이트는 한국어 단답을 대량 탈락**: 조사 분리로 토큰 중첩이 안 생기는 "뭐 좀?"류 후보가 min_distinctive/coverage 조건에 걸림. 완화 시 커버 +31%p, rerank 기여 3배(+0.028→+0.072).
4. **kosgd/kodialog의 저성능은 태스크 특성**: 맥락-다음발화/반응형 단답은 어휘·벡터 모두 신호 빈약. 임베딩 단독에서도 kosgd 0.175. **운영 도메인(장문·어휘 풍부한 기억 회수)에서는 koalpaca/기계독해처럼 높을 것으로 추정** (실제 Hermes 대화 기억은 문장·문서형).
5. **비용 구조**: B는 코퍼스 크기에 Jev 요청이 정비례(10k 스팬이면 10배). A는 쿼리당 1회 고정.

## 5. 개선 방향 후보 (타 AI 평가 요청)

**전제**: 운영 중인 a8m 임베딩 모델 유지. Jev 호출은 현행 1회/쿼리에서 **2~5배(쿼리당 2~5회) 증가 허용**. 코퍼스 크기에 비례하는 무제한 증가(B식)는 불가.

1. **Jev rerank를 "choice 1개" → "후보 풀 relevance 배치 스코어링"으로 교체**
   - B의 `judge_many`(noul relevance) 방식을 차용하되, full-corpus가 아니라 **A의 lane pool(50~70개)에만** 적용.
   - 예상: 호출 1→1~2(배치), 풀 내부 순위 정확도 대폭 개선. 커버 80.6% 내에서 1위 정확도를 끌어올리는 핵심 후보.
2. **2-stage rerank**: 1차 relevance로 top-10~20 선별 → 2차 choice로 최종 1개. (호출 2~3)
3. **lane pool 순위 개선**: RRF가 임베딩 단독(0.672)보다 나쁨(0.467) — RRF 가중치/lane budget 재튜닝, 또는 vec lane 단독 순위를 기본으로 FTS를 보조로. (Jev 호출 변화 없음)
4. **lane pool 커버리지 확대**: vec top-k 60→100+, 쿼리 확장(Jev/LLM로 쿼리 동의어 확장 후 임베딩). 커버 80.6%→90%+ 목표. (Jev +1~2/쿼리 또는 무증가)
5. **Jev 결정 캐시**: B는 decision cache 65,536 참조 — 반복 쿼리/후보 재평가 비용 절감.
6. **rerank 풀 크기 상한 튜닝**: choice는 풀 70개에서 정확도 저하(0.100) — 풀을 20~30으로 제한 후 choice, 또는 풀 전체 relevance. 크기-정확도 관계 실측 필요.
7. **운영 도메인 재검증**: kodialog/kosgd(반응형 단답)는 운영과 다른 태스크 — **실제 Hermes 세션 기억을 코퍼스로 한 재실측**을 통해 "실제 손실"을 분리 측정.

**타 AI에게 받고 싶은 답**:
- (a) 1번(choice→relevance 배치)이 이 데이터에서 기대할 수 있는 Acc@1 상한은? 다른 함정?
- (b) 3번 RRF 순위 저하(0.672→0.467)의 원인과 최선의 병합 전략?
- (c) 4번 쿼리 확장 vs vec top-k 확대 중 커버리지 개선 효율이 높은 쪽?
- (d) Jev 호출 예산 2~5배에서 최고의 효율 지점(정확도/비용/지연)은?
- (e) 이 실측 설계에서 놓친 비교 조건이나 오류는?

### 5.1 RRF pool 내 정답 rank 분포 (1번 개선안의 기대치 산정 근거)

커버된 145/180 아이템에서, RRF lane pool 순서 기준 정답 위치:

| rank 구간 | 건수 | 비율 | 개선 가능성 |
|---|---|---|---|
| top 1 | 84 | 58% | 이미 1위 (choice와 무관) |
| top 2-5 | 17 | 12% | **relevance rerank로 구제 가능** |
| top 6-20 | 29 | 20% | relevance rerank로 일부 구제 가능 |
| top 21+ | 15 | 10% | 순위 과다 — rerank로도 어려움 |

- 데이터셋별 (커버 중 top1 / 2-5 / 6-20 / 21+): koalpaca 34/3/3/0, 기계독해 40/0/0/0, kodialog **2/10/17/10**, kosgd 8/4/9/5.
- **해석**: ① 기계독해·koalpaca는 이미 RRF가 완벽(1위 74/80) — rerank 불필요. ② **kodialog이 문제의 핵심**: 커버 39개 중 1위 2개뿐, 2-20위 27개 — relevance rerank가 이 27개를 살리면 kodialog 0.100→~0.45+ 기대. ③ **전체 기대 상한 ≈ (84+17+~15)/180 ≈ 0.64** (worst: 84/180=0.47, best: 130/180=0.72). PR 0.806에 근접하려면 **lane pool 커버(80.6%) 자체를 90%+로** 올려야 함 (§5 후보 4).
- choice(현행)가 relevance보다 나쁜 이유: **1개 선택은 top2-5의 정답을 못 건지고, 70개 풀에서 1개를 고르는 분류 오류가 큼** (kodialog 0.100이 증거). relevance는 풀 전체를 점수화해 순위만 교정하면 되므로 오류 여지가 작음.
