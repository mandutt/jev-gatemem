## 2. 게이트별 최종 판정

| 게이트 | 결과 | 판정 |
|---|---|---|
| G1 RAM ≤ 500MB | 전 모델 실패 (baseline 948 / koen 597 / bekko 617) | **게이트 자체 재정의 필요** — 500MB는 파일 크기 기준 추정치에 근거했으나 실측 커밋은 ORT arena+인터프리터 상주 포함. 현행 모델(948MB)도 2배 초과하므로 "500MB 절대 기준"은 실효성 없음. 사전 등록 §7.3의 절감률(ram_reduction_pct) 주 지표로 전환: **koen -37% / bekko -35%** (둘 다 의미 있는 절감) |
| G2 지연 | 3모델 전부 ms 단위 통과 (p95 1.5~4.4ms) | 게이트 사실상 무효화될 정도로 여유 |
| G3 품질 | 미완료 — 하이브리드 F1(격리 데몬 경유) 미측정. vec-only gold로 대체 측정한 결과: MRR bekko 0.780 > koen 0.726 > baseline 0.665 (유의성 미확보) | 확정 판정 보류 — gold 50 확장 또는 하이브리드 실측 필요 |
| G4 트랩 | T1/T2는 **세트 결함**으로 전 모델 실패(baseline 포함) → 세트 재설계 필요. T3는 유일하게 캘리브레이션된 게이트: **koen 9 > bekko 8 > baseline 7** — 현행 모델의 부정 구분 약점을 두 후보가 모두 개선 | 세트 v2 재설계 후 재측정 권고 |
| G5 int8 drift | 양쪽 100% (≥98%) | ✅ 완벽 통과 |
| G6 무결성 | 후보별 독립 DB — 혼합 벡터 0건 | ✅ |

## 3. 실험 중 발견 사항 (계획 이탈 포함)

1. **bekko ONNX 그래프는 L=8192 기준 선할당 구조**: 클램프 512 적용해도 배치 64에서 동일 9.66GB 버퍼 요청(OOM). **배치 4 필수**. 이는 시퀀스 길이 문제도 ORT 버그도 아닌 그래프 구조 특성 — a-AI/b-AI의 길이 가설은 클램프 재인덱스 실험으로 기각됨.
2. **클램프 512 + 배치 4 재인덱스로 bekko 807.6s → 278.9s 단축(65%)** — 최종 bekko DB는 클램프 적용본.
3. **granite 3변형 전부 실패 확정**: 정적 quint8 hang(6h+), fp16→DQL INVALID_GRAPH, fp32→동적 int8 재인덱스 중 76GB OOM. 탈락 최종 확정.
4. **T1/T2 트랩 세트 결함**: baseline까지 실패하는 세트였음 — 절대 게이트로 부적합. T3만 유효.
5. fastembed 0.8.0의 baseline preset이 CLS→mean pooling 경고를 내지만, 운영 환경도 같은 버전 경로이므로 3모델 비교 조건은 동일.

## 4. 채택 권고 (사용자 승인 대기)

### 권고: **bekko-a8m** (조건부)

근거:
1. **vec-only gold 3지표 전부 1위** (R@1 0.75 / MRR 0.780) — 단, 통계 유의성은 미확보(20쿼리)
2. **단건 지연 3배 빠름** (p95 1.5ms vs 4.2ms) — 실운영 recall 경로 부담 최소
3. RAM 절감 baseline 대비 -35% (koen -37%와 사실상 동급, WS 기준 -53%)
4. 접두어 불필요(대칭형) — koen의 `query:`/`passage:` 접두어 운영 부채 회피
5. T3 부정역전 8/10 — baseline 7/10 대비 개선

조건:
- (a) gold 세트 50+로 확장해 MRR 우위가 유지되는지 확인 (b-AI 권고, 통계력)
- (b) 하이브리드 F1(격리 데몬) 실측 — vec-only만으로 판정 불가
- (c) T1/T2 세트 v2 재설계 후 재측정 — 특히 koen과의 비교가 한국어 트랩에서 어떻게 갈리는지
- (d) 재인덱스 운영 절차에 "배치 4 필수" 문서화 (ONNX 그래프 특성)

### 대안: koen-e5-tiny

- T3 부정역전 최강(9/10), T1/T2 상대 우위, RAM 절감 최대(-37%)
- E5 접두어 관리 필요 — 파이프라인에 role 강제 인터페이스가 있어 관리 가능하나 운영 복잡도 추가
- bekko 대비 MRR -0.055 (CI는 동등 구간)

### 유지 판정 대상 아님: baseline
- 모든 지표에서 후보 2종에 뒤지거나 동급, RAM은 2배, T3 최하위.

## 5. P3b 보강 측정 (2026-10-01, gold 50 + 하이브리드 스윕)

### 5.1 vec-only gold 50

|---|---|---|---|

| Recall@5 | 0.62 | 0.84 | 0.82 |

- **baseline vs koen: [-0.240, -0.072]** — **후보 2종의 baseline 대비 우위가 통계적으로 유의 확정** (20쿼리 때와 달리 0 미포함)

### 5.2 하이브리드 F1 스윕 (BM25 char-level + vec, offline 단일 프로세스)

| 구성 | R@1 | R@5 | R@10 | MRR |
|---|---|---|---|---|
| lex-only BM25 | 0.78 | 0.86 | 0.96 | 0.824 |
| **hybrid koen vw=0.3** | **0.78** | 0.90 | **0.98** | **0.843** |
| hybrid koen vw=0.5 | 0.74 | 0.92 | 0.96 | 0.821 |
| hybrid koen vw=0.7 | 0.72 | 0.86 | 0.94 | 0.789 |
| hybrid bekko vw=0.3 | 0.76 | 0.90 | 0.96 | 0.827 |
| hybrid bekko vw=0.5 | 0.76 | 0.90 | 0.96 | 0.829 |
| hybrid bekko vw=0.7 | 0.72 | 0.90 | 0.98 | 0.803 |

해석:
- **lex-only BM25(MRR 0.824)가 vec-only 전 모델보다 높음** — gold 쿼리가 기억 원문 오프닝 라인에서 파생되어 어휘 일치에 유리한 **구조적 편향**이 있음(쿼리-문드 중복). 절대 비교는 과대평가 경계.
- 그럼에도 **하이브리드가 최고치**: koen vw=0.3 (MRR 0.843, R@10 0.98).
- **vec_weight 0.3(어휘 레인 우세)이 양쪽 모두 최적** — 현행 Mnemosyne 하이브리드 vec 가중치 설정과 대조 필요.

### 5.3 보강 후 채택 권고 변동 없음 (강화됨)

- bekko 권고 유지. gold 50에서도 bekko가 vec-only 3지표 중 R@1/MRR 1위, 하이브리드 최적점에서 koen과 격차 0.014~0.016 (동등 구간).
- 결정적 차별점은 여전히 운영 특성: bekko p95 1.5ms + 접두어 불필요 + 배치 4 재인덱스 절차만 문서화하면 됨.
- 남은 조건: (c) T1/T2 세트 v2 — 세트 설계 문제로 모델 비교 본질에 영향 감소. S4 진입 전 필수 조건에서 권고로 하향 가능.

### 5.4 granite 사후 탐색 (배치 4, 10분 타임아웃)

- 정적 quint8 원본이 배치 4에서는 hang 없이 63.8초간 1,030건 인덱싱 진행(이전 배치 64 무한 hang과 다른 행동) — **그러나 같은 OOM으로 사망: 50.8GB 버퍼 요청** (배치 8의 76.2GB → 정확히 B 비례).
- 배치 1 extrapolation ≈ 12.7GB/배치 — RAM 15.6GB의 80%를 단건이 요구. **운영 투입 불가 확정, 재시도 종료.**

## 6. X1 외부 데이터셋 검증 (2026-10-01, KoDialogBench response_selection)

> 동기: 내부 gold(오프닝 라인 파생)는 쿼리-문서 어휘 중복 편향 존재 → 독립 생성 외부 데이터셋으로 순위 재검증.

- 구조: 쿼리 = 대화 맥락(마지막 6턴), 후보 5개(정답 1 + hard negative 4), **Accuracy@1 + MRR**
- 스크립트: `s3_x1_kodialog.py` (결과: `cand/s3_x1_kodialog.json`)

| 모델 | 전체 Acc@1 | 전체 MRR | 임베딩 7,200건 시간 |
|---|---|---|---|
| **koen** | **0.622** | **0.758** | 40s |
| baseline | 0.587 | 0.741 | 37s |

서브코퍼스별: koen이 4종 전체에서 baseline 대비 우위·동급, a8m은 empathetic_dialogues에서 특히 약함(0.563 vs koen 0.650).

**핵심 발견 — 순위 뒤집힘**: a8m의 내부 gold-50 1위(MRR 0.772)는 외부 벤치에서 재현되지 않음(최하위). 내부 gold의 어휘 중복이 a8m에 유리하게 작용했을 가능성 + 극소형(7.7M) 도메인 일반화 한계. koen은 양쪽 모두 준수(일반화 검증).

## 7. X2 다국어 열화 프로브 (2026-10-01)

> 동기: 배포 시 다른 사용자의 다국어 사용 가능성. koen(한·영 전용 어휘 프루닝) vs a8m(100+ 언어) 다국어 리스크 정량화.

- 설계: 5 언어(ja/zh/es/fr/de) × "timeout 설정" 시나리오, 10-way 선택(gold 1 + 동일 언어 방해 9), vec-only vs 하이브리드(BM25 vw=0.3)
- 스크립트: `s3_x2_multilingual.py` (결과: `cand/s3_x2_multilingual.json`)

| 언어 | baseline vec/hyb | koen vec/hyb | a8m vec/hyb |
|---|---|---|---|
| 일본어 | 1 / 1 | **0** / 1 | 1 / 1 |
| 중국어 | 1 / 1 | **0** / 1 | 1 / 1 |
| 스페인어 | 1 / 1 | 1 / 1 | 1 / 1 |
| 프랑스어 | 1 / 1 | 1 / 1 | 1 / 1 |
| 독일어 | 1 / 1 | 1 / 1 | 1 / 1 |

**결론**:
- koen 열화는 전반적 소폭 저하가 아니라 **CJK 문자계에서 치명적** — 어휘 프루닝(한·영 ~3만 토큰)의 직접 결과. 라틴 문자권은 무난.
- char-level BM25 하이브리드(vw=0.3)가 koen의 CJK 실패를 **이 조건(10-way, 쿼리-문서 어휘 공유)에서는 완전 복구** — 단, 방해 문서 대규모(수백+)·완전 의미적 유추 질의(어휘 공유 없음)에서는 복구 보장 없음.
- a8m은 전 언어 vec 단독 통과 — 100+ 언어 백본(mmBERT)의 실질 검증.

| baseline | 242.4s | 40.4건/s |

**해석:**
- **kodialogbench 순위는 X1 재현** (baseline 0.585 vs a8m 0.560 — X1의 0.587/0.583과 동일 방향). 대화 응답 선택은 baseline이 근소 우위.
- **그 외 도메인(지시문/문서 QA)은 a8m 압도적 우위** — 특히 기계독해 1.0 vs 0.37: baseline은 문서 오프닝 유사 검색에서 긴 문서(2,206자)를 제대로 매칭하지 못하고, a8m은 정확히 회수.
- **kosgd 양 모델 저조**(0.086/0.052)는 **과제 특성**(맥락-다음 발화는 어휘 중복 거의 없는 일반응답 예측) 때문 — 모델 결함 아님. 상대 우위는 a8m(1.65배).
- 종합: **운영 도메인(장기기억 회수)에서 a8m이 baseline 대비 우위 유지** — X1의 우려(대화 응답만)는 도메인 한정이며, 지시문·문서 회수에선 a8m이 명확히 낫다. S4 채택(§9) 재확인 보강.

## 8c. PerfectRecall vs 내 구현 — 격리 A/B 비교 (2026-10-01)

> 동기: PerfectRecall(`arslanr-com/perfectrecall`, 이하 PR)은 "Jev full-corpus 스캔" 설계의 독립 포크. 같은 스크래치 코퍼스·쿼리로 내 파이프라인(lane pool + Jev rerank)과 품질/비용/지연/메모리를 격리 비교.

**프로토콜 (격리 준수):**
- 스크래치 전용 SQLite DB (코퍼스 419 스팬: kodialogbench 60아이템×5후보 + koalpaca 40 + kosgd 40 + 기계독해 40), 쿼리 180, 동일 seed
- 실 Hermes/데몬/DB/config 무접촉 —내 venv(jev-mem) 코드는 스크래치 DB에 바인딩, PR venv는 자체 클론 사용
- Jev 엔드포인트 동일 (`api.typesafe.ai/v1/systemone`, typesafe provider), 동일 키
- 내 파이프라인: `build_lane_pool`(FTS+vec+imp+graph RRF) → `_filter_and_rank` → `jev_rerank(choice)` — 라이브 `pipeline._retrieve/_rerank` 로직 그대로
- PR: `jev_recall._rank(query, corpus)` = `jev.relevance` 전체 코퍼스 배치 (cutoff=0, 전부 유지)
- **스크래치 DB 벡터 백필 필수**: PR venv로 생성된 DB는 `memory_embeddings` 0건 → a8m으로 419건 백필 후 재측정 (내 vec lane 활성화)

**결과:**

| 지표 | 내 구현 (lane+rerank) | PerfectRecall (full-scan) | 비고 |
|---|---|---|---|
| Acc@1 | **0.489** | **0.806** | PR 우위 |
| MRR | 0.556 | 0.849 | PR 우위 |
| 지연 | **0.23 s/쿼리** | 0.38 s/쿼리 | 내 구현 -40% |
| Jev 요청/180쿼리 | **179** | 1,800 | PR 10배 |
| 추정 비용 | **$0.00~0.02** | $0.05~0.15 (usage.cost 미반환) | 요청 10배 |
| 프로세스 메모리 | a8m 모델 **615 MB** | **12 MB** (모델 없음) | PR 50배 적음 |

**원인 분석 (필수):**
1. **lane pool 커버리지 상한 = PR Acc**: raw pool(필터 전 RRF) 정답 커버 145/180(80.6%) = **Acc 0.467 ≈ PR Acc 0.806**. 즉 PR은 "전체 코퍼스를 Jev에 노출"하므로 lane이 놓치는 19.4%도 판정 가능 — 내 정확도 하드캡은 lane pool 누락.
2. **`_filter_and_rank` 어휘 게이트가 한국어 단답을 추가 탈락**: min_distinctive=2 + min_coverage=0.30은 조사 분리된 한국어 반응형 후보("뭐 좀?")를 토큰 중첩 부족으로 다수 제거 (pool 60→4~11). 그나마 남은 pool도 짧은 의미 매칭은 vec 유사도가 낮아 top-60 미포함.
3. **내 rerank는 pool 내 1등만 lift**: pool에 정답이 없으면(19.4%) 회생 불가, 있어도 choice가 틀리면 손해 — 순 효과는 +0.02 (0.467→0.489).
4. **PR은 임베딩 모델 없이 SQLite 스트리밍 스캔** → 메모리 12MB, 대신 쿼리당 요청이 코퍼스 크기에 정비례 (180쿼리=1,800요청, 코퍼스 10배면 요청도 10배).

**결론:**
- **회수 정확도는 PR 우위 (0.806 vs 0.489)** — lane pool 누락(19.4%) + 어휘 게이트가 원인. 다만 이 태스크(짧은 한국어 대화 응답 5지선다)는 **내 운영 도메인(장기기억 회수)과 다름** — §8b의 koalpaca(0.980)/기계독해(1.000)와 같은 지시문·문서 회수에선 내 파이프라인이 lane pool 커버리지가 높아 격차가 작을 것으로 예상.
- **비용/자원은 내 구현 압도적 우위** (요청 1/10, 지연 -40%, 임베딩 모델 615MB 대신 PR은 12MB지만 recall 품질을 Jev API 비용으로 구매).
- **설계 트레이드오프가 실측으로 확정**: PR="전부 Jev에 던진다"(정확도↑, 비용∝코퍼스), 내 구현="lane pool로 좁힌다"(비용 고정, 누락 리스크). 내 운영 환경(15.6GB RAM, 비용 민감)에서는 lane+게이트가 적합하나, **lane pool 커버리지 80%대 단점은 인지하고 운영 문서에 명시** (query가 길고 어휘 풍부한 실제 메모리 회수에선 커버리지가 더 높음 — §8b 참조).

**측정 레이어 명확화 (사용자 지적으로 재검증, 2026-10-01):**
- §8b/X3의 Acc@1은 **임베딩 모델 단독**(쿼리 vs 후보 전체 직접 유사도) 수치 — 이 A/B의 180개 아이템으로 재현 시 **a8m 단독 Acc@1 0.672 / MRR 0.759** (kodialog 0.567, koalpaca 1.0, kosgd 0.175, 기계독해 1.0). X3의 kodialog 0.560(1,200개)과 동일 방향·유사 수준.
- 이 A/B의 내 구현 수치(0.489)는 **전체 운영 파이프라인**(lane pool 60개 컷 → 어휘 게이트 → Jev rerank) 성능 — X3와 **측정 대상이 다름** (단독 모델 vs 전체 파이프라인). 파이프라인 손실 요인: ① lane pool이 후보 60개로 선별(정답 탈락 시 회생 불가) ② `_filter_and_rank`가 한국어 짧은 후보를 어휘 중첩 부족으로 추가 탈락 ③ Jev rerank는 살아남은 pool 내 1위만 lift.
- **결론**: 모델 단독 성능(0.672)은 X3와 일관. 파이프라인 전체(0.489)는 어휘 게이트 + lane pool 커버 한계로 낮아짐 — 이건 **모델 회귀가 아니라 파이프라인 설계 특성**. koalpaca/기계독해(문장·문서)는 파이프라인에서도 거의 손실 없음(모델 단독 1.0).

**게이트 스윕 후속 측정 (2026-10-01, Jev 180요청 추가):**
- `_filter_and_rank` 파라미터 6종 스윕 (md×mc = 2/0.30 ~ 0/0.0) — Jev 없이 $0:

| 변형 (md/mc) | Acc@1 | MRR | 정답커버 | 평균 pool |
|---|---|---|---|---|
| 2/0.30 (현행) | 0.461 | 0.529 | 89/180 (49.4%) | 23.4 |
| 1/0.30 | 0.461 | 0.529 | 89/180 | 23.4 |
| 2/0.15 | 0.478 | 0.530 | 116/180 (64.4%) | 38.8 |
| 1/0.15 | 0.478 | 0.530 | 116/180 | 38.8 |
| 1/0.0 | 0.467 | 0.527 | 145/180 (80.6%) | 68.7 |
| 0/0.0 | 0.467 | 0.527 | 145/180 | 69.7 |

- **게이트 완화(md=1, mc=0) + Jev rerank 실측** (180쿼리, 요청 180):

| 설정 | Acc@1 | MRR | 정답커버 |
|---|---|---|---|
| 원래 게이트 + rerank | 0.489 | 0.556 | 49.4% |
| **완화 게이트 + rerank** | **0.539** | **0.584** | **80.6%** |
| PR full-scan | 0.806 | 0.849 | 100% |

- **해석:**
  1. 어휘 게이트 완화는 **커버 +31%p, Acc +0.05** — 게이트가 한국어 단답 탈락의 실질 원인임을 실증 (rerank 기여도도 0.028→0.072로 3배 증가 — 풀 커버리지↑ → rerank가 일할 기회↑).
  2. 그래도 PR에 0.267 뒤짐: **lane pool RRF가 반응형 단답을 상위에 못 올림** (kodialog 커버 39/60인데 rerank 후에도 Acc 0.100 — 풀에 있어도 1위로 못 끌어올림). Jev choice는 풀 70개 중 1개 고르기라 신호가 약함.
  3. koalpaca 0.975 / 기계독해 1.0 — 어휘 풍부 도메인은 완화 후 거의 최대. **운영 도메인(문장·문서 기억)에서는 완화가 이득.**
  4. **권고: `_filter_and_rank` 기본값을 (1, 0.0)으로 완화** — 커버/Acc 이득, pool 증가(23→69)는 Jev choice 지연에 미미(0.23→0.28s/쿼리). 다만 최종 1위 정확도 향상을 원하면 rerank를 choice→relevance 스코어링으로 교체(PR식, 비용↑)가 필요 — 트레이드오프는 §8c 결론과 동일.
